# pos-engine: internal note for the P2 planner

Status: written at the end of phase P1a (engine extraction). English, internal, not part of the dossier. Source of truth is the code: `crates/pos-engine/src/engine.rs`, `events.rs`, `background.rs`, `install.rs`; the command map below is generated by `python3 scripts/android/check_ipc_wrappers.py --map`.

## 1. What the engine is

`crates/pos-engine` holds everything the till does that is not a window: opening the database, signing events with the FDM, tickets, reports, HubRise, settings. It has no Tauri dependency and no platform conditional compilation: platform differences are `EngineConfig` inputs. The Linux shell `src-tauri` wraps each command as a `#[tauri::command]` (one call each, `src-tauri/src/ipc`); the Android shell (`android/rust/pos-ffi`, phase P2) calls the same functions.

The harness of the integration tests (`crates/pos-engine/tests`) is `crates/pos-engine-testkit` (`publish = false`, a dev-dependency of `pos-engine` only, outside the certified binary).

The fiscal behaviour is the certified one: P1a is a pure move, guarded by the test inventory and the normalised FDM journals (`docs/android/DECISIONS.md`, PD2, PD3).

## 2. EngineConfig

`Engine::open(EngineConfig) -> anyhow::Result<Engine>`. The Android column is what `pos-ffi` is planned to pass (decisions of the plan, P2); it is not implemented yet.

| Field | Type | Linux value (`src-tauri/src/main.rs`) | Android value (`pos-ffi`, P2) |
|---|---|---|---|
| `paths` | `EnginePaths` (`data_dir`, `db`, `backups`) | `EnginePaths::under(paths::data_dir())`: `pos.db` and `backups/` under `paths::data_dir()`: `PILI_POS_DATA_DIR`, else `STATE_DIRECTORY` (systemd, `/var/lib/pili-pos` in production), else `<user data dir>/pili-pos` | `EnginePaths::under(<app files dir>)` |
| `config` | `ConfigSource` | `config_source_from(PILI_POS_CONFIG, /etc/pili-pos/pos.json)`: `File(path)` from the variable, else `File("/etc/pili-pos/pos.json")` when it exists, else `DevelopmentDefaults` (warned, TEST identity) | `ConfigSource::Bundle(<path of pos.json in the provisioning bundle>)`: loaded like `File`, then every relative file or directory path is resolved against the bundle directory |
| `events` | `Arc<dyn EventSink>` | `TauriEventSink` (forwards each event to the webview under its topic; the app handle is set in Tauri's `setup`, events before it are dropped) | A sink that queues events for the app to pull through the FFI (`NullSink` exists for tests and headless runs) |
| `timers` | `EngineTimers` (`auto_z`, `mail_outbox`, `printer_status_read`) | `EngineTimers::default()`: automatic Z checked every 60 s, mail outbox every 30 s (`delivery::OUTBOX_INTERVAL`), printer status read 500 ms (`DEFAULT_STATUS_READ_TIMEOUT`) | `auto_z` and `mail_outbox` default; `printer_status_read` about 2 s (PD37): on the Android network path the DLE EOT answer often arrives after 500 ms (spike S4) |
| `identity` | `SoftwareIdentity` (the `posSwVersion` of every event and ticket) | `SoftwareIdentity::new(concat!("pili-pos/", env!("CARGO_PKG_VERSION")))`, so `pili-pos/1.0.0` during P1a | `pili-pos-android/X.Y.Z` (the Android app version). Required: there is no default; never read from `pos.json` |
| `http_tls` | `HttpTls` (`Platform` or `RootsOnly(Vec<DER>)`) | `HttpTls::Platform` (system trust store) | `HttpTls::RootsOnly(<bundled webpki roots, DER>)`. The engine never infers the mode from the OS; an empty `RootsOnly` is refused by `Engine::open`. The FDM mTLS client (`pos-fiscal::fdm_tls`, module2 X.509 v1 certificates) is configured separately by `pos.json` |
| `device_id_override` | `Option<String>` | `None` (the `device_id` of `pos.json` is kept) | `Some(<Sunmi serial>)`; replaces `device_id` after the configuration is loaded; trimmed, 1 to 600 characters, else `Engine::open` fails |
| `support_program` | `Option<PathBuf>` | `paths::support_program()` (the RustDesk binary when installed) | `None`: the support commands answer "not available" and a start is refused |

`printer_status_read` is the wait for each DLE EOT answer after a print (PD37); every engine print path passes it to `pos-print`. `PrinterStatus.status_known` is false when the printer did not answer both queries in time (the other fields are then the optimistic default, not a printer report). `get_settings` carries `posSwVersion` (the identity string, AM Art. 47) for the login screen.

Related types, all re-exported at the crate root: `EnginePaths::under(data_dir)`, `ConfigSource::{File, Bundle, DevelopmentDefaults}`, `EngineTimers`, `HttpTls`, `HttpTlsError`, `SoftwareIdentity`, `IdentityError` (the last four live in `pos-fiscal`).

Cargo features: `hubrise` and `peppol` (both default). Every shipped build has `hubrise`; the cert set is `--no-default-features --features cert` on `pili-pos`, which forwards to `pos-engine`. The Android library is expected to be built like the cert set: HubRise in, `peppol` out (the two `peppol only` commands below are then absent).

## 3. Lifecycle

1. `Engine::open(cfg)`:
   1. checks `http_tls` and validates `device_id_override`;
   2. creates the data directory and takes an exclusive lock on `<data_dir>/engine.lock` (`File::try_lock`; an empty file, no data). A second engine on the same data directory fails with `engine already open: <path>`: two engines would sign with the same counters;
   3. opens `pos.db`, runs the migrations, repairs what a crash left (orphaned checkouts, online orders left in signing);
   4. loads the configuration (`ConfigSource::load`), applies the device id override, logs FDM setting problems, builds the mail client, the HubRise switch and the shared HTTP client from `http_tls`.
   Any error is fatal: a fiscal terminal never boots with a partial or wrong identity.
2. `engine.start_background(&tokio::runtime::Handle)`: spawns on the given runtime, once the shell has a runtime and (on Linux) its event handle:
   - automatic Z of a business day left open (at start, then every `timers.auto_z`);
   - digital ticket mail outbox (every `timers.mail_outbox`; idle when no mail client is configured);
   - presence worker: signs the clock-ins that logins queue (`SessionRules` presence queue), one after another in arrival order; an employee already on shift is skipped, a failure raises `presence-failed`. The queue's receiver is taken once, so a second `start_background` spawns no second worker;
   - HubRise poller and HubRise outbox (`hubrise` feature; idle while the installation switch is off).
3. Commands: `commands::<module>::do_*(&AppState, ...)`. `Engine` derefs to `AppState`, so a shell passes `&engine` (Tauri manages the `Engine`; the wrappers call `do_*(state.inner(), ...)`). Commands are plain functions: no runtime is needed for the sync ones; the async ones need a Tokio runtime. `lock_session` registers the active order (event P, see `set_active_order` and `leave_order`), then closes the session without clocking the operator out, and emits `session-locked`. A successful `login` or `login_with_new_pin` queues the clock-in (PD34): the presence worker signs it, the login never waits for the FDM. `end_shift` replaces the UI's login, `work_out`, logout sequence: it checks the PIN like `login`, signs the clock-out and always closes the session.
4. `engine.shutdown()`: cancels the shutdown token; the loops finish on their own. `engine.take_background_tasks()` hands out the join handles for a shell (or test) that wants to await them.
5. Drop: dropping the `Engine` closes `engine.lock` and releases the lock. The background tasks hold an `Arc<AppState>` (database connections), not the `Engine`: for a restart in the same process, call `shutdown()`, await `take_background_tasks()`, then drop, before opening again on the same data directory.

Offline helpers for a shell, in `pos_engine::install`: `init_db(db_path, seed)`, `check_config(env_path, production_path)`, `check_config_source(&ConfigSource)`, `apply_seed(conn, sql)`.

## 4. Events

The engine tells its shell about things that happen outside a command call through `EventSink::emit(EngineEvent)`. It is called from the background tasks and from the FDM client, so it must not block. `EngineEvent::topic()` gives the name the UI listens to (unchanged from the Tauri-era strings).

| Topic | Variant | Payload type | Raised by | Feature |
|---|---|---|---|---|
| `fdm-sign-messages` | `FdmSignMessages` | `pos_fiscal::fdm_client::SignMessages` (`mutation`, `booking_date`, `warnings`, `informations`) | after any signed event, when the FDM attached warnings or informations (`state.rs`) | always |
| `session-locked` | `SessionLocked` | `commands::session::SessionLocked` (`reason` `manual` or `idle`, `orderError`) | `lock_session` (the idle lock reaches the same code): the active order is registered, then the session closes | always |
| `presence-failed` | `PresenceFailed` | `commands::social::PresenceFailed` (`insz`, `clockIn`, `error`) | the presence worker, when the clock-in queued by a login was not registered (FDM error or refusal); the login itself is unaffected | always |
| `webshop-order-received` | `WebshopOrderReceived` | `pos_hubrise_types::CallbackEvent` | HubRise poller, order created | `hubrise` |
| `webshop-order-updated` | `WebshopOrderUpdated` | `CallbackEvent` | HubRise poller, order changed | `hubrise` |
| `catalog-updated` | `CatalogUpdated` | `CallbackEvent` | menu updated from the HubRise catalog | `hubrise` |
| `catalog-rejected` | `CatalogRejected` | `CallbackEvent` | catalog has issues, menu unchanged | `hubrise` |
| `catalog-awaiting-adoption` | `CatalogAwaitingAdoption` | `CallbackEvent` | first sync over a hand-entered menu, waits for a manager | `hubrise` |

`events::event_for_outcome` maps a poller `DispatchOutcome` to an event (`Ignored` raises none). Payloads are serde types (the Tauri sink serialises them as before); `CallbackEvent` carries `id`, `resource_type`, `event_type`, `created_at`, `previous_state`, `new_state` and the flattened remaining fields.

## 5. Remaining environment reads (PD13)

The engine reads the process environment in two places only (`docs/android/DECISIONS.md`, PD13). The engine otherwise reads neither environment variables nor fixed paths; there is no `env!`/`option_env!` in it (the version comes from `identity`).

| Where | Variable | Effect | On Android |
|---|---|---|---|
| `commands/hubrise.rs::oauth_config` | `HUBRISE_OAUTH_BASE_URL`, `HUBRISE_BASE_URL`, `HUBRISE_POS_CLIENT_ID`, `HUBRISE_POS_CLIENT_SECRET`, `HUBRISE_POS_REDIRECT_URI`, `HUBRISE_POS_SCOPE` | development fallback, used only in debug builds (`cfg!(debug_assertions)`) when the `hubrise` section of `pos.json` is absent; a release build without that section answers `hubrise_not_configured` | reached only by a debug build without the `hubrise` section |
| `commands/support.rs::support_home` | `RUNTIME_DIRECTORY`, else `std::env::temp_dir()` | `HOME` given to the support program (the only production `temp_dir()` use) | reached only with a support program, which Android never passes (`support_program: None`) |

The shell's own reads (`PILI_POS_CONFIG`, `PILI_KIOSK`, `.env` through `dotenvy`, the log filter) are in `src-tauri`, not in the engine.
