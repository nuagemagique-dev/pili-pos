# pos-engine: internal note for the P2 planner

Status: written at the end of phase P1a (engine extraction), final pass at the end of phase P1b (UI rules moved into the engine); the Linux version is 1.0.0, the first Linux filing (user, 2026-10-10). English, internal, not part of the dossier. Source of truth is the code: `crates/pos-engine/src/engine.rs`, `events.rs`, `background.rs`, `install.rs`; the command map below is generated by `python3 scripts/android/check_ipc_wrappers.py --map`.

## 1. What the engine is

`crates/pos-engine` holds everything the till does that is not a window: opening the database, signing events with the FDM, tickets, reports, HubRise, settings. It has no Tauri dependency and no platform conditional compilation: platform differences are `EngineConfig` inputs. The Linux shell `src-tauri` wraps each command as a `#[tauri::command]` (one call each, `src-tauri/src/ipc`); the Android shell (`android/rust/pos-ffi`, phase P2) calls the same functions.

The Android facade is described in `docs/android/FFI.md` (implemented in P2).

The harness of the integration tests (`crates/pos-engine/tests`) is `crates/pos-engine-testkit` (`publish = false`, a dev-dependency of `pos-engine` only, outside the certified binary).

The fiscal behaviour is the certified one: P1a is a pure move, guarded by the test inventory and the normalised FDM journals (`docs/android/DECISIONS.md`, PD2, PD3).

### EngineTimers

`EngineTimers` (in `engine.rs`, `Default` = the Linux values) holds the five intervals the engine itself needs. Tests set shorter ones.

| Timer | Used by | Linux value (default) | Android value (decided so far) |
|---|---|---|---|
| `auto_z` | automatic Z of a business day left open (at start, then every interval) | 60 s | default |
| `mail_outbox` | digital ticket outbox retry | 30 s (`delivery::OUTBOX_INTERVAL`) | default |
| `idle_lock` | idle lock (PD35): time without `user_activity` or login before the session is locked | 300 s | default |
| `fdm_poll` | FDM status monitor base interval while the FDM answers (PD36); doubles per unanswered check up to 10 times | 30 s (then 60, 120, 240, 300 s) | default |
| `printer_status_read` | wait for each DLE EOT answer after a print (PD37) | 500 ms (`DEFAULT_STATUS_READ_TIMEOUT`) | about 2 s (spike S4: the answer often arrives after 500 ms on the network path) |

`fdm_poll` is the interval of the FDM status monitor while a session is open and the FDM answers (PD36); while it does not answer the wait doubles with each failed check, up to 10 times the value (30 s, 60, 120, 240, then 300 s with the default). `printer_status_read` is the wait for each DLE EOT answer after a print (PD37); every engine print path passes it to `pos-print`. `PrinterStatus.status_known` is false when the printer did not answer both queries in time (the other fields are then the optimistic default, not a printer report). `get_settings` carries `posSwVersion` (the identity string, AM Art. 47) for the login screen.

Related types, all re-exported at the crate root: `EnginePaths::under(data_dir)`, `ConfigSource::{File, Bundle, DevelopmentDefaults}`, `EngineTimers`, `HttpTls`, `HttpTlsError`, `SoftwareIdentity`, `IdentityError` (the last four live in `pos-fiscal`).

Cargo features: `hubrise` and `peppol` (both default). Every shipped build has `hubrise`; the cert set is `--no-default-features --features cert` on `pili-pos`, which forwards to `pos-engine`. The Android library is expected to be built like the cert set: HubRise in, `peppol` out (the two `peppol only` commands below are then absent).

## 3. Lifecycle

1. `Engine::open(cfg)`:
   1. checks `http_tls` and validates `device_id_override`;
   2. creates the data directory and takes an exclusive lock on `<data_dir>/engine.lock` (`File::try_lock`; an empty file, no data). A second engine on the same data directory fails with `engine already open: <path>`: two engines would sign with the same counters;
   3. opens `pos.db`, runs the migrations, repairs what a crash left (orphaned checkouts, online orders left in signing);
   4. loads the configuration (`ConfigSource::load`), applies the device id override, logs FDM setting problems, builds the mail client, the HubRise switch and the shared HTTP client from `http_tls`.
   Any error is fatal: a fiscal terminal never boots with a partial or wrong identity.
2. `engine.start_background(&tokio::runtime::Handle)`: spawns on the given runtime, once the shell has a runtime and (on Linux) its event handle:
   - automatic Z of a business day left open (at start, then every `timers.auto_z`);
   - digital ticket mail outbox (every `timers.mail_outbox`; idle when no mail client is configured);
   - presence worker: signs the clock-ins that logins queue (`SessionRules` presence queue), one after another in arrival order; an employee already on shift is skipped, a failure raises `presence-failed`. The queue's receiver is taken once, so a second `start_background` spawns no second worker;
   - idle lock (PD35, `background::run_idle_lock`): waits until the last activity plus `timers.idle_lock`, re-arming at every `user_activity` and every login; when the time has really run out and a session is open it runs the lock path (`session::lock`, reason `idle`: the active order is registered, the session closes, `session-locked` is emitted). Without a session, and after a lock, it waits for the next touch instead of polling; a failed registration never prevents the lock;
   - FDM status monitor (PD36, `background::run_fdm_monitor`): polls the FDM Status only while a session is open (`access::open_session` and `close_session` notify `SessionRules::session_changed`). Without a session it waits and sends nothing. A session that opens is checked at once (the backoff starts again); then it waits `poll_delay(timers.fdm_poll, failures)` (`fdm_poll` while the FDM answers, `fdm_poll * 2^n` up to `fdm_poll * 10` after `n` consecutive unanswered checks) before each check, or until an explicit `fdm_check_now` or a session change makes it recompute from now. When the session closes it stops, and the stored health loses its `nextCheckAt`. Every check goes through `checkout::do_check_fdm_status` (its 20 s cache is kept), is classified (below), stored, and emitted as `fdm-status`;
   - HubRise poller and HubRise outbox (`hubrise` feature; idle while the installation switch is off).
Background loops at a glance (all stop at `shutdown()`):

| Loop | Trigger | What it does | Raises |
|---|---|---|---|
| automatic Z | start, then every `auto_z` | closes a business day left open | none |
| mail outbox | every `mail_outbox` | retries queued digital ticket mails, clears addresses after 72 h | none |
| HubRise poller | HubRise poll interval (`hubrise` feature) | pulls webshop orders and catalog changes | `webshop-order-*`, `catalog-*` |
| HubRise outbox | HubRise outbox interval (`hubrise` feature) | sends queued status updates | none |
| presence worker | a login queues a clock-in | signs the S clock-in unless the employee is on shift | `presence-failed` |
| idle lock | `idle_lock` after the last activity | locks an unattended session (reason `idle`) | `session-locked` |
| FDM monitor | session opens, then `poll_delay(fdm_poll, failures)` | checks and classifies the FDM status while a session is open | `fdm-status` |

3. Commands: `commands::<module>::do_*(&AppState, ...)`. `Engine` derefs to `AppState`, so a shell passes `&engine` (Tauri manages the `Engine`; the wrappers call `do_*(state.inner(), ...)`). Commands are plain functions: no runtime is needed for the sync ones; the async ones need a Tokio runtime. `lock_session` registers the active order (event P, see `set_active_order` and `leave_order`), then closes the session without clocking the operator out, and emits `session-locked`. `user_activity` (sync, needs no session, cheap: the UI forwards activity at most once per second) restarts the idle time; every login restarts it too. A successful `login` or `login_with_new_pin` queues the clock-in (PD34): the presence worker signs it, the login never waits for the FDM. `end_shift` replaces the UI's login, `work_out`, logout sequence: it checks the PIN like `login`, signs the clock-out and always closes the session. `fdm_check_now` (async, needs no session: the login screen and the retry button) checks the FDM now, stores and emits the health and makes the monitor schedule from now; `fdm_health` (sync) returns the last known health, `null` before the first check. Both replace the explicit checks of `ui/src/stores/fdm.ts`.
4. `engine.shutdown()`: cancels the shutdown token; the loops finish on their own. `engine.take_background_tasks()` hands out the join handles for a shell (or test) that wants to await them.
5. Drop: dropping the `Engine` closes `engine.lock` and releases the lock. The background tasks hold an `Arc<AppState>` (database connections), not the `Engine`: for a restart in the same process, call `shutdown()`, await `take_background_tasks()`, then drop, before opening again on the same data directory.

Offline helpers for a shell, in `pos_engine::install`: `init_db(db_path, seed)`, `check_config(env_path, production_path)`, `check_config_source(&ConfigSource)`, `apply_seed(conn, sql)`.

## 4. Events

The engine tells its shell about things that happen outside a command call through `EventSink::emit(EngineEvent)`. It is called from the background tasks and from the FDM client, so it must not block. `EngineEvent::topic()` gives the name the UI listens to (unchanged from the Tauri-era strings).

| Topic | Variant | Payload type | Raised by | Feature |
|---|---|---|---|---|
| `fdm-sign-messages` | `FdmSignMessages` | `pos_fiscal::fdm_client::SignMessages` (`mutation`, `booking_date`, `warnings`, `informations`) | after any signed event, when the FDM attached warnings or informations (`state.rs`) | always |
| `session-locked` | `SessionLocked` | `commands::session::SessionLocked` (`reason` `manual` or `idle`, `orderError`) | `lock_session`, or the idle loop after `timers.idle_lock` without activity (reason `idle`): the active order is registered, then the session closes | always |
| `fdm-status` | `FdmStatus` | `commands::fdm_monitor::FdmHealth` (`connected`, `answered`, `severity` `blocking`, `warning` or `info`, `code`, `mandatory`, `checkedAt`, `nextCheckAt`, the times RFC 3339 UTC) | the FDM monitor after each check, and `fdm_check_now` (PD36); `nextCheckAt` is `null` without a session | always |
| `presence-failed` | `PresenceFailed` | `commands::social::PresenceFailed` (`insz`, `clockIn`, `error`) | the presence worker, when the clock-in queued by a login was not registered (FDM error or refusal); the login itself is unaffected | always |
| `webshop-order-received` | `WebshopOrderReceived` | `pos_hubrise_types::CallbackEvent` | HubRise poller, order created | `hubrise` |
| `webshop-order-updated` | `WebshopOrderUpdated` | `CallbackEvent` | HubRise poller, order changed | `hubrise` |
| `catalog-updated` | `CatalogUpdated` | `CallbackEvent` | menu updated from the HubRise catalog | `hubrise` |
| `catalog-rejected` | `CatalogRejected` | `CallbackEvent` | catalog has issues, menu unchanged | `hubrise` |
| `catalog-awaiting-adoption` | `CatalogAwaitingAdoption` | `CallbackEvent` | first sync over a hand-entered menu, waits for a manager | `hubrise` |

`events::event_for_outcome` maps a poller `DispatchOutcome` to an event (`Ignored` raises none).

### FDM status classification

`commands::fdm_monitor::classify` turns the status JSON of `do_check_fdm_status` into an `FdmHealth`, with the rules of `checkStatus` and `pickPrimaryMessage` of the former Vue store. A message with `showPos` MANDATORY must not auto-dismiss (certification manual section V), hence `mandatory`. The search follows JavaScript `find()`: it takes the first matching item and then needs its `extensions.code`; an item without a code is not skipped for the next one.

| Vue branch | Engine result (`severity`, `code`, `mandatory`, `connected`, `answered`) |
|---|---|
| `connected === false` or a truthy `error` (transport failure), or an `Err` of the check | `blocking`, the error text (`FDM_NOT_OPERATIONAL` without one), `true`, not connected, not answered |
| first MANDATORY error with a code | `blocking` if the code is `BUFFER_FULL`, `FDM_LOCKED`, `FDM_NOT_OPERATIONAL` or `UNKNOWN_POS`, else `warning`; that code; `true` |
| else first error whose `showPos` is not NEVER, with a code | same severity rule; that code; `false` |
| else first MANDATORY warning with a code | `warning`, that code, `true` |
| else first warning whose `showPos` is not NEVER, with a code | `warning`, that code, `false` |
| nothing above (errors that are all NEVER are ignored) | `info`, no code, `false` |
| `initialized === false` | not connected; with no code from above the code is `FDM_NOT_INITIALIZED` (severity as above, so `info`) |
| any answer | answered; connected unless `initialized === false` or the severity is `blocking` |

The poll delay is `poll_delay(base, failures)`: `base` for 0, else `min(base * 2^failures, base * 10)` (30, 60, 120, 240, 300, 300 s for failures 0 to 5), where `failures` counts consecutive unanswered checks (an answer, even with an error, resets it). Payloads are serde types (the Tauri sink serialises them as before); `CallbackEvent` carries `id`, `resource_type`, `event_type`, `created_at`, `previous_state`, `new_state` and the flattened remaining fields.

## 5. Remaining environment reads (PD13)

The engine reads the process environment in two places only (`docs/android/DECISIONS.md`, PD13). The engine otherwise reads neither environment variables nor fixed paths; there is no `env!`/`option_env!` in it (the version comes from `identity`).

| Where | Variable | Effect | On Android |
|---|---|---|---|
| `commands/hubrise.rs::oauth_config` | `HUBRISE_OAUTH_BASE_URL`, `HUBRISE_BASE_URL`, `HUBRISE_POS_CLIENT_ID`, `HUBRISE_POS_CLIENT_SECRET`, `HUBRISE_POS_REDIRECT_URI`, `HUBRISE_POS_SCOPE` | development fallback, used only in debug builds (`cfg!(debug_assertions)`) when the `hubrise` section of `pos.json` is absent; a release build without that section answers `hubrise_not_configured` | reached only by a debug build without the `hubrise` section |
| `commands/support.rs::support_home` | `RUNTIME_DIRECTORY`, else `std::env::temp_dir()` | `HOME` given to the support program (the only production `temp_dir()` use) | reached only with a support program, which Android never passes (`support_program: None`) |

The shell's own reads (`PILI_POS_CONFIG`, `PILI_KIOSK`, `.env` through `dotenvy`, the log filter) are in `src-tauri`, not in the engine.

Linked card terminal (EFT, `crates/pos-eft`, `commands/eft.rs`, migration 27 `eft_payments`). With a `payment_terminal` section in `pos.json` (`get_settings` carries `paymentTerminal`, the kind, else the field is absent):
- `eft_pay(order_id, amount_cents) -> EftPayment` (async, cashier): stores the payment as `sent` BEFORE asking the terminal, then stores the answer (`approved`, `declined`, `cancelled`, `unknown`; `not_sent` plus an error when nothing was charged). Refused: `eft_not_configured`, `order_not_open`, `eft_amount_invalid` (not above what the order's other approved terminal payments leave due), `eft_pending` (a payment of the till is `sent` or `unknown`), an FDM that is not operational now (checked fresh, never from the cache; the "FDM not connected" refusal, or `FDM_ANSWER_PENDING`), then the terminal's own `eft_busy`, `eft_unreachable`, `eft_rejected`.
- `eft_abort() -> ()` (async, cashier): asks the terminal to stop the payment in `sent`; Ok when none. `eft_check(id) -> EftPayment` (async, any user): asks `status(reference)` of a `sent` or `unknown` payment and stores the answer; an approval for another amount than the request stays `unknown`. `list_eft_payments(order_id) -> Vec<EftPayment>` (sync, any user): approved-unused and unresolved payments, oldest first.
- `EftPayment` JSON (snake_case): `id`, `order_id`, `amount_cents`, `status`, `card_type` (`debit|credit|unknown|null`), `brand`, `terminal_reference`, `authorisation_code`, `masked_pan`, `meal_voucher` (bool: the stored brand is Edenred, Pluxee, Monizze or Payflip, `pos_eft::brand::is_meal_voucher`), `detail`, `created_at`, `used`.
- `check_payment_terminal() -> PaymentTerminalStatus {configured, kind, connected, busy, detail}` (async, no login: the start-up checks ask before anyone is in): `configured: false` without a probe when no terminal is linked; else `Terminal::check` (charges nothing). `AppState::eft_line` (a tokio mutex) is held by `eft_pay` and `eft_check` for their whole terminal exchange; the probe only `try_lock`s it and answers `busy: true, connected: true` without probing while it is held (a terminal serves one connection at a time). `eft_abort` never takes it. Header light (30 s, like the printers, and again when a payment starts or ends) and start-up row only when configured.
- At start a `sent` row becomes `unknown`. `PaymentPart.eft_payment_id` (optional) names the approved payment a card part settles; `checkout` and `webshop_handover_order` refuse (`eft_payment_not_usable`) a part that is not an approved, unused payment of this order, card, for its exact amount, and a sale that leaves an approved payment of the order out (also a sale closed unpaid); `eft_pending` while one waits. The payment line is `AUTOMATIC`, type from the card type, `provider` the brand, `reference` the terminal's id: debit ("2", "Card"), credit ("6", "Credit card"), unknown ("7", "Card (type unknown)"), meal-voucher card ("3", "Meal voucher", type `CHEQUE_MEAL`, the identity of the manual meal voucher; the `payments` history row is `meal_voucher`; the part stays method `card`); a card typed by hand stays ("2", "Card", `CARD_DEBIT`, `MANUAL`). The payments are marked used in the sale's archive transaction (`PendingContext::Sale.eft_payment_ids`), also when the FDM's answer is lost and comes later. An order edit (`remove_order_line`, `update_order_line_quantity`) that would bring the total under the sum of the order's approved unused payments is refused and rolled back (`eft_below_charged|amount=17,00`), and any edit is refused while a payment of the order is `sent` or `unknown` (`eft_edit_pending`); `webshop_reject_order` and `webshop_close_cancelled_order` (which corrects every line) are refused (`eft_below_charged`) once a card was charged on the order. Adding lines is always allowed.
- `list_unsettled_card_payments() -> [UnsettledCardPayment {payment_id, order_id, order_type, table_number, amount_cents, brand, created_at}]` (sync, any logged-in user): the approved payments of every order that no sale has settled, oldest first. A card payment approved but not yet used by a sale is money taken that no ticket records; its order's sale settles it later, possibly after a Z. The Z is never blocked by it (the auto-Z always runs); both UIs list these payments in the Z step ("Paiements par carte encaissés mais pas encore enregistrés dans une vente") and mark their orders ("Carte encaissée") on the table plan and the takeaway list.
- Tests: feature `eft-scripted` of `pos-engine` (enabled by `pos-engine-testkit` only) adds `AppState::eft_terminal_override`, a `pos_eft::scripted::Script` used in place of the configured terminal; no shipped build has it.
