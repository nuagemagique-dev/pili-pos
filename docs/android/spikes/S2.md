# Spike S2: UniFFI hello world (Rust core on Android)

Branch `android/p0-S2`, spike code under `spikes/s2/` (never merged to main, only this report).
Run date: 2026-10-06, macOS Apple M1, emulator AVD `pili_api33` (API 33, arm64-v8a, google_apis).

## Verdict

GO. Everything in the plan's FFI shape works end to end in an R8-minified release APK on API 33:
own tokio runtime driven through `rt.spawn` / `spawn_blocking` + JoinHandle, error enum mapped to a
sealed Kotlin exception, broadcast-backed `EventStream` with `Resync` on lag, panics surfacing as
`InternalException` with the process surviving, coroutine cancellation not aborting the in-flight
Rust task, 16 KB page alignment, and a plain JVM test against the host dylib.

Four things the production plan must absorb (details in "Gotchas"):

1. uniffi 0.32.2 Kotlin bindings do NOT verify the contract version or API checksums on first use. They
   only do so inside `uniffiEnsureInitialized()`. The wrapper must call it once at engine open, otherwise a
   mismatched `.so` goes straight into native code (observed: JVM SIGSEGV).
2. Library-mode bindgen needs the symbol table: it fails on a `--strip-all` / `--strip-unneeded` `.so`.
   Generate from the unstripped (or `--strip-debug`) file, which is what we do.
3. The `--config` file format changed in 0.32 (global format, `[crates.<name>.bindings.kotlin]`). The old flat
   file is silently ignored with a warning, so `android = true` is lost without noticing.
4. Panic messages go to stderr, which Android does not forward to logcat. The text still reaches Kotlin in the
   `InternalException` message, but a production build should install a panic hook that logs.

## The Rust crate (`rust/hello-ffi`)

- `crate-type = ["cdylib", "lib"]`, `uniffi::setup_scaffolding!()`, `#[uniffi::export]` proc-macros only, no UDL.
- `HelloEngine` object owns a `tokio::runtime::Runtime` (multi-thread, 2 workers, thread name `hello-rt`).
  The runtime sits in an `Option` and `Drop` calls `shutdown_background()`: dropping a `Runtime` from inside an
  async context panics, and UniFFI can drop the last `Arc` on whatever thread the Kotlin Cleaner or a runtime
  thread happens to be.
- `add_async`: `self.rt().spawn(async { sleep; ... })` then `handle.await`. `hash_blocking`:
  `self.rt().spawn_blocking(|| ...)` then `handle.await`. No `async_runtime = "tokio"` attribute; the UniFFI
  future that Kotlin polls is a plain future whose only await point is the `JoinHandle`, so it does not need a
  tokio context.
- `HelloError` (`#[derive(uniffi::Error, thiserror::Error)]`): `NotFound { id }`, `Invalid { code, reason }`,
  `Closed`, `TaskFailed { detail }`. Kotlin gets `sealed class HelloException` with one subclass per variant.
- `EventStream::next()` async, backed by `tokio::sync::broadcast::Receiver` behind a `tokio::sync::Mutex`;
  `RecvError::Lagged(n)` becomes `HelloEvent::Resync { missed: n }`, `RecvError::Closed` becomes `None`.
- Panics: `panic_now` (sync), `panic_in_future` (inside the polled future body), `panic_in_task` (inside a
  spawned task, mapped to `HelloError::TaskFailed` through `JoinError::is_panic`).
- `slow_sign(ms)`: spawns a task that bumps an atomic counter, awaited through the JoinHandle. Used to prove
  cancellation semantics.
- Cargo feature `mismatch` changes one function signature, only for `check_mismatch.sh`.
- `[profile.android-release]`: `inherits = "release"`, `panic = "unwind"`, `opt-level = "z"`, `lto`,
  `codegen-units = 1`, `strip = "none"`, `debug = "line-tables-only"`.
  `rust/.cargo/config.toml` adds `-C link-arg=-Wl,-z,max-page-size=16384` for `aarch64-linux-android`.

## Build and Gradle wiring

Prerequisites: `spikes/s2/android/local.properties` with `sdk.dir=...` (gitignored) or `ANDROID_HOME`, and
`export ANDROID_NDK_HOME=$HOME/Library/Android/sdk/ndk/27.1.12297006 CARGO_TARGET_DIR=$HOME/.cache/pili-android/S2`.

Standalone (no Gradle): `spikes/s2/build_so.sh` runs, from `spikes/s2/rust`:

```
cargo ndk -t arm64-v8a -o <app/build/generated>/jniLibs build --profile android-release -p hello-ffi
cargo run --profile android-release -p uniffi-bindgen -- generate \
   --library $CARGO_TARGET_DIR/aarch64-linux-android/android-release/libhello_ffi.so \
   --language kotlin --config android-uniffi.toml --out-dir <app/build/generated>/uniffi-android
cargo build --release -p hello-ffi                      # host dylib
cargo run --release -p uniffi-bindgen -- generate --library .../release/libhello_ffi.dylib \
   --language kotlin --config jvm-uniffi.toml --out-dir <app/build/generated>/uniffi-jvm
```

Gradle (`./gradlew assembleRelease` in `spikes/s2/android`), `app/build.gradle.kts`:

- `cargoNdkBuild` (Exec): the cargo ndk command above. Output `.so` goes to `app/build/generated/jniLibs/arm64-v8a/`
  and the unstripped original stays in `$CARGO_TARGET_DIR/aarch64-linux-android/android-release/`. Inputs are the
  Rust sources/manifests, so it is up to date when nothing changed (about 1 s).
- `uniffiBindgenAndroid` (Exec, `dependsOn(cargoNdkBuild)`): library-mode bindgen from that same unstripped `.so`,
  `--config android-uniffi.toml` (`android = true`, `android_cleaner = true`), output
  `app/build/generated/uniffi-android/uniffi/hello_ffi/hello_ffi.kt`. Never committed.
- `sourceSets.main`: `java.srcDir(<uniffi-android>)`, `java.srcDir(spikes/s2/shared)`, `jniLibs.srcDir(<jniLibs>)`.
  `srcDir` carries no task dependency, so `tasks.named("preBuild") { dependsOn(uniffiBindgenAndroid) }`.
- Both Exec tasks put `~/.cargo/bin` first on `PATH` (see gotchas) and pass `CARGO_TARGET_DIR` / `ANDROID_NDK_HOME`.
- AGP strips the packaged `.so` itself (`stripReleaseDebugSymbols`, NDK 27.1) so the APK carries the stripped file
  while bindgen read the unstripped one. Release is `isMinifyEnabled = true`, signed with the debug key.

`:jvmtest` (`./gradlew :jvmtest:test`): `cargoBuildHost` (`cargo build --release -p hello-ffi`) then
`uniffiBindgenJvm` (generated Kotlin into `jvmtest/build/generated/uniffi-jvm`, `compileKotlin` depends on it),
`jna.library.path` points at `$CARGO_TARGET_DIR/release` and JNA loads `libhello_ffi.dylib`.

### Plain JVM test (host dylib)

`./gradlew :jvmtest:test` passes 9/9 (`HostLibTest`: load, async spawn, spawn_blocking, error mapping, event stream,
resync, stream closes, cancellation, panic). The same `shared/Scenarios.kt` as the APK, Kotlin generated from the host
`libhello_ffi.dylib`, plain `jna:5.19.1` jar. Rust panic text appears on the test's stderr
(`thread 'hello-rt' panicked at hello-ffi/src/lib.rs:181:17`), unlike on Android. Generated Kotlin for the JVM uses
`java.lang.ref.Cleaner` (no `SystemCleaner` reference).

### Checksum mismatch detection

`spikes/s2/check_mismatch.sh` builds the host dylib with `--features mismatch` (one signature differs), generates the
bindings from the normal build, and runs `ChecksumMismatchTest` against the mismatched dylib:

```
S2-JVM mismatch result: java.lang.ExceptionInInitializerError -> UniFFI API checksum mismatch: try cleaning and rebuilding your project
ChecksumMismatchTest > mismatchIsDetectedAtLoad PASSED
```

Without `uniffiEnsureInitialized()` the same mismatch is NOT detected: the first call
(`plainFn("x")` into a function that now takes two arguments) crashed the JVM with
`SIGSEGV ... uniffi_hello_ffi_fn_func_plain_fn+0x2c`. The `load` scenario therefore calls `uniffiEnsureInitialized()`
first, in the APK and in the JVM test, so any bindings/`.so` drift fails the load test.

`llvm-readelf -lW` on the packaged `libhello_ffi.so` (and on the unstripped one, and on `libjnidispatch.so`): every
`LOAD` segment has `Align 0x4000`. `zipalign -c -P 16 -v 4 app-release.apk` prints `Verification successful`

Library-mode bindgen on stripped files: it works on `--strip-debug` output (generated Kotlin byte-identical to the

`No UniFFI metadata found in <file>` (the metadata lives in `UNIFFI_META_*` symbols). So: always generate from the
unstripped `.so` that cargo produced, as the build does, and never from the file taken out of the APK.

## Gotchas

- **Checksum mismatch (see above).** uniffi 0.32.2 moved the contract-version and API-checksum checks into
  `IntegrityCheckingUniffiLib.init`, which only `uniffiEnsureInitialized()` triggers; the `UniffiLib` init that used to
  run them is now empty. Call `uniffiEnsureInitialized()` at engine open and keep the JVM test that loads a deliberately
  mismatched library. Messages: `UniFFI API checksum mismatch: try cleaning and rebuilding your project` and
  `UniFFI contract version mismatch`. They surface wrapped in `ExceptionInInitializerError` on the first access.
- **Bindings must come from the exact unstripped `.so`.** Library mode reads metadata from the symbol table; the build
  does cargo ndk, then bindgen on the cargo output, then lets AGP strip the packaged copy. Both bindgen and `pos-ffi`
  pin `uniffi = "=0.32.2"` (workspace dependency) so the generator and scaffolding cannot drift.
- **Cleaner on API 33.** `android = true` plus `android_cleaner = true` makes the generated code use
  `android.system.SystemCleaner` (API 33+, our minSdk) with a JNA-cleaner fallback below that, one shared cleaner
  thread for the library instead of one per `java.lang.ref.Cleaner`. The generated file then references
  `androidx.annotation.RequiresApi`, so the module needs `androidx.annotation:annotation` or Kotlin compilation fails with
  `Unresolved reference 'RequiresApi'`. `AndroidSystemCleaner` is present in the R8 mapping. Still call
  `destroy()`/`use {}` for the engine (and streams) explicitly: Cleaner timing is not deterministic.
- **uniffi 0.32 `--config` format.** Must be `[crates.<crate_name>.bindings.kotlin]` (see `rust/android-uniffi.toml`). The old
  flat `[bindings.kotlin]` file is ignored with only `warning: ... looks like an old-style --config override file`, so
  the Android flavour was silently not generated until fixed. A per-crate `uniffi.toml` next to `Cargo.toml` is still read.
- **JNA AAR vs jar.** Android must use `net.java.dev.jna:jna:<ver>@aar` (carries `libjnidispatch.so` per ABI, 16 KB aligned
  in 5.19.1); the plain jar has no Android native dispatch. The JVM test must use the plain jar (macOS/Linux dispatch
  libs inside). Do not put both on one classpath. JNA ships no consumer ProGuard rules.
- **R8/JNA rules** as tabulated above. Symptoms to recognise: `Can't obtain peer field ID for class com.sun.jna.Pointer`
  (JNA classes renamed) and `Structure.getFieldOrder() ... does not provide enough names` (uniffi Structure classes renamed).
  R8 8.13.25 must be forced (copied buildscript classpath); the 8.9.1 bundled one cannot read Kotlin 2.2 metadata.
- **Coroutine cancellation on an in-flight spawn.** Cancelling the Kotlin coroutine makes the generated code call
  `rust_future_cancel` + `free`, which drops the UniFFI future and therefore the `JoinHandle`. Dropping a tokio
  `JoinHandle` detaches the task, it does NOT abort it, so the spawned work runs to completion (`completed=1` after the
  cancel). This is exactly the "a cancelled coroutine never aborts a sign in flight" requirement, and it holds only
  because the work is spawned on the engine runtime and not awaited inline in the UniFFI future. The caller never sees that
  result (no way to read it after cancellation), so idempotency/recovery of the effect is the engine's business.
- **Panics.** With `panic = "unwind"` UniFFI's `catch_unwind` converts both sync and in-future panics to
  `InternalException(message)`, even for functions that return `Result<_, HelloError>`, so `InternalException` is a separate
  channel from the error enum and must be caught by the gateway (plan: mark the engine Fatal and restart). A panic inside a
  spawned task is isolated by tokio and only visible as `JoinError`, which the code must map itself. With `panic = "abort"`
  the process would die instead. On Android the Rust panic message is not in logcat (stderr is not forwarded); only the
  exception message has it. Install a panic hook with `android_logger`/`__android_log_write` in production.
- **Runtime drop.** `HelloEngine.destroy()` ends up in `Drop`; a bare `Runtime` field would panic if dropped from an async
  context. The `Option<Runtime>` + `shutdown_background()` pattern also closes the broadcast channel, so open `EventStream`s
  return `None` from `next()`.
- **rustup vs Homebrew cargo.** `/opt/homebrew/bin/cargo` comes first on this machine's PATH and ignores the rustup targets
  of `rust-toolchain.toml` (`can't find crate for std ... aarch64-linux-android may not be installed`). The scripts and
  Gradle tasks prepend `~/.cargo/bin`.
- **`android.sdk` for Gradle.** Needs `local.properties` (`sdk.dir`) or `ANDROID_HOME`; the Gradle daemon does not read
  the interactive shell profile. The generated Kotlin tries to run `ktlint` and prints
  `Unable to auto-format hello_ffi.kt using ktlint` (harmless; pass `--no-format` to silence it).
- **Gradle `srcDir` and generated code.** `sourceSets.srcDir` has no producer wiring; hook `preBuild` (or use
  `variant.sources` with a proper task output) so `compileKotlin`, `lint` and `mergeJniLibFolders` see generated files.
- **Timings (M1).** Cold `cargo ndk` build of this crate: about 2.5 minutes (uniffi + tokio, LTO, `opt-level = "z"`); cold
  Gradle `assembleRelease` including dependency download about 3.5 minutes; warm rebuild after a Kotlin edit about 10 s.
