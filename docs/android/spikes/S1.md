# Spike S1: cross-compile the engine crates for Android (arm64, API 33)

Phase P0 of the Sunmi D3 Pro port plan. Scope: can `pos-db`, `pos-fiscal`,
`pos-print`, `pos-mail`, `pos-hubrise` and `pos-catalog` be built with
Rust 1.99.0 and NDK r27 for `aarch64-linux-android`, and do their tests pass
on an arm64 API 33 emulator. Spike code is not merged; this report and the
scripts under `spikes/s1/` (kept for reproduction, raw outputs in
`spikes/s1/results/`) are the only artefacts.

## Verdict

- All six crates cross-compile in release mode with no source change and no
  tool beyond `cargo-ndk` and the NDK. `aws-lc-sys` and `libsqlite3-sys`
  (bundled) built first time with the NDK clang.
- The only build failure was a host tooling one: Homebrew's `rustc` shadows
  rustup's on this Mac and has no Android std (fix: put `~/.cargo/bin` first).
- All 6 crates' test binaries build for Android (debug). On the emulator,
  **every test that does not read a host fixture path passes**. 35 tests in 9
  `pos-fiscal` integration binaries fail only because `CARGO_MANIFEST_DIR` is
  baked as an absolute macOS path. With the path redirected to the device and
  the fixtures pushed, all of them pass too (see "Failures").
- Test totals match the host `-- --list` counts for every crate.
- One real Android behaviour difference was seen: reqwest's rustls platform
  verifier panics (`Expect rustls-platform-verifier to be initialized`), the
  JNA gotcha from plan point 4. It is reachable from `pos-fiscal` when the FDM
  CA file cannot be read. No other test exercises HTTPS (see S3 relevance).
- None of the six crates depends on `tauri`; `src-tauri` is not needed to
  build them.

## Feature set (matches the cert build)

The cert build is `cargo build --release --no-default-features --features cert`
for `pili-pos` (`cert = ["custom-protocol", "hubrise"]`, and `hubrise` enables
`pos-db/hubrise`, `dep:pos-hubrise`, `dep:pos-catalog`, `dep:pos-hubrise-types`,
`dep:qrcode`). Output of

```bash
cargo tree -p pili-pos --no-default-features --features cert -e features \
  --target aarch64-linux-android
```

filtered to the six crates (and their direct feature nodes, unique lines):

```text
pos-catalog feature "default"
pos-db feature "default"
pos-db feature "catalog-sync"      (from pos-catalog and from pos-db/hubrise)
pos-db feature "hubrise"           (from pos-hubrise and from pili-pos/hubrise)
pos-fiscal feature "default"
pos-hubrise feature "default"
pos-mail feature "default"
pos-print feature "default"
```

So `pos-db` needs `--features hubrise` (it implies `catalog-sync`); the other
five use default features (none of them declares optional features;
`pos-catalog` and `pos-hubrise` turn on `pos-db/catalog-sync` and
`pos-db/hubrise` through their own dependency lines). Every crate in this
spike therefore uses these features. The full tree is 3.7k lines and includes
`src-tauri` dev-dependency edges (mocks); it is not reproduced here.

### aws-lc-sys, libsqlite3-sys, cc/cmake, bindgen

No failure. Evidence from the build script output
(`target/.../build/aws-lc-sys-*/output`):

- `aws-lc-sys 0.45.0` (via `aws-lc-rs 1.18.1`, pulled by `pos-fiscal`'s direct
  `rustls`/`aws-lc-rs` dependencies) was compiled by the `cc` crate with the
  NDK clang (`CC_aarch64-linux-android = .../ndk/27.1.12297006/.../bin/clang`).
  It produced `libaws_lc_0_45_0_crypto.a` (6.2 MB) including the aarch64 asm
  objects. The output has no cmake invocation (only `rerun-if-env-changed`
  lines for `AWS_LC_SYS_CMAKE_BUILDER`) and no bindgen invocation (pre-generated
  bindings are used for this target), so neither host cmake 4.4.4 nor
  libclang/bindgen is needed.
- `libsqlite3-sys 0.38.2` with the `bundled` feature compiled `sqlite3.c` with
  the same clang, no extra variable.
- `rustls-platform-verifier-android 0.2.0` is compiled and linked as a normal
  dependency (it is the Android half of reqwest's verifier; see F3).

### Failures and fixes

**F1. Wrong `rustc` on PATH (environment only).**
`which -a rustc` gives `/opt/homebrew/bin/rustc` (Homebrew 1.99.0, host std only)
before `~/.cargo/bin/rustc` (rustup, has `aarch64-linux-android`). With the
default PATH, `cargo ndk ... build` fails on the first crate:

```text
error[E0463]: can't find crate for `core`
  = note: the `aarch64-linux-android` target may not be installed
  = help: consider downloading the target with `rustup target add aarch64-linux-android`
error: could not compile `serde_core` (lib) due to 1 previous error
```

Root cause: the Homebrew toolchain shadows the rustup proxy, so
`rust-toolchain.toml` is ignored. Fix: `export PATH="$HOME/.cargo/bin:$PATH"`
(`spikes/s1/env.sh`). CI and the future Android Gradle build should invoke
`rustup run 1.99.0 cargo ...` or set the PATH explicitly.

**F2. Harness mistake (not a project issue).** Sourcing `cargo ndk-env` and then
running plain `cargo test --target aarch64-linux-android` fails at link time
(`error: linking with '/Users/brunomoyse/.cargo/bin/cargo-ndk' failed`) because
cargo-ndk's linker proxy only works inside a `cargo ndk` invocation. All
builds in this report therefore go through `cargo ndk ...`. Note that
`cargo ndk` swallows cargo's `--message-format=json` and the `Executable ...`
lines, so `spikes/s1/test_build.sh` finds the test executables as the ELF files
in `deps/` newer than a marker (after touching the crate's `lib.rs`). A later
Gradle/cargo-ndk integration that needs the paths must not rely on cargo-ndk
echoing them.

**F3. Not a build failure, a runtime one:** see "Android behaviour difference"
below.

No source change was needed anywhere, so there is no patch to describe for the
builds. `git diff main...HEAD` touches only `spikes/s1/**` and this file.

## Running on the emulator

`/data/local/tmp/s1/<crate>/`, `chmod 755`, then
`adb shell "cd /data/local/tmp/s1/<crate> && ./<bin> --test-threads=1"` (and a

(and every crate has 0 doc-tests on the host). The host baseline is
`cargo test -p <crate> --no-fail-fast` and `-- --list` on macOS
(`spikes/s1/results/host-*.txt`); all host runs pass.

### Does pushing the fixtures to the same absolute path work?

Not on this emulator. The compiled-in path is
`/Users/brunomoyse/.../crates/pos-fiscal`, so the fixtures would have to exist
under `/Users/...` on the device, and `/` is a read-only dm-verity ext4 mount.
Tried: `adb root`, `adb disable-verity` + reboot, `adb remount` (succeeds, but
only overlays `/system`, `/product`, `/system_ext`, `/system_dlkm`),
`blockdev --setrw /dev/block/dm-0` and `mount -o remount,rw /` (`'/dev/block/dm-0'
is read-only`), then `mkdir /Users` still gives `Read-only file system`. A
pushed fixture tree under `/data/local/tmp` cannot be reached through the
baked path.

### Does an env var work?

No env var exists in these tests: the paths come straight from
`env!("CARGO_MANIFEST_DIR")`, except
`ticket_examples` (`TICKET_EXAMPLES_DIR`, an output dir, unrelated) and
`e2e_staging` (`PILI_STAGING_*`, ignored).

### What does work (throwaway experiment, not committed)

`spikes/s1/fixture_patch.sh <dir>` copies the workspace (without `.git`, `ui`,
`docs/SUBMISSION_ARTIFACTS`) to a scratch directory and, with `sed`, replaces
`env!("CARGO_MANIFEST_DIR")` in the test sources by the string
`"/data/local/tmp/s1/ws/crates/<crate>"` (11 files: 10 in
`crates/pos-fiscal/tests`, 1 in `crates/pos-fdm-mock/tests`). The nine affected
`pos-fiscal` binaries were rebuilt (213 s in a fresh target dir, 2.4 GB, deleted
afterwards) and run with these fixtures pushed under `/data/local/tmp/s1/ws`:

- `docs/` (47 MB, only the `20260821_UC_*` folders are read),
- `crates/pos-fdm-mock/fixtures/` (`module2`, `tls`),
- `crates/pos-fiscal/tests/fixtures/module2_tls/` (`ca.crt`, `server.crt`).

Result: **all 9 binaries pass**, 1+3+6+3+2+6+8+6+6 = 41 tests (the 35 failures
plus the 6 that already passed in the same binaries), with `--test-threads=1`
and with default threads. So the failures are purely path-related.

Patch to propose for the real source (not applied here, nothing under
`crates/` changed): replace each `env!("CARGO_MANIFEST_DIR")` in the test
helpers with a helper such as

```rust
fn fixture_root() -> std::path::PathBuf {
    std::env::var_os("PILI_FIXTURE_ROOT")
        .map(Into::into)
        .unwrap_or_else(|| std::path::PathBuf::from(env!("CARGO_MANIFEST_DIR")))
}
```

(one shared `tests/common` function, the env var pointing at the device copy of
the workspace layout). On the host nothing changes. This is only needed if
the Android CI wants to run these nine fixture suites on a device; they already
run on the host, which is where the certification evidence is produced.

### Android behaviour difference: rustls-platform-verifier

In the first patched run `fdm_https_mock::an_fdm_signed_by_another_ca_is_refused`
failed with a different cause than the other tests, because
`tests/fixtures/module2_tls/ca.crt` had not been pushed yet:

```text
thread 'an_fdm_signed_by_another_ca_is_refused' panicked at
  rustls-platform-verifier-0.7.1/src/android.rs:90:10:
Expect rustls-platform-verifier to be initialized
```

With an unreadable CA file `FdmClient::tls_from_config`
(`crates/pos-fiscal/src/fdm_client.rs`) logs and returns `None`, so
`from_config` builds a plain reqwest client on its default rustls verifier, and on Android that verifier needs a JNIEnv and a Context
that nothing has provided (a `JNI_OnLoad` is never run for a JNA-loaded
library). After pushing the CA file the same test passes (the custom-CA
path of `fdm_tls` does not use the platform verifier). This confirms plan
point 4 on real Android code: any HTTPS call that reaches reqwest's built-in
verifier panics at the first handshake.

## S3 relevance: HubRise and Scaleway TEM TLS are not covered

`pos-hubrise` and `pos-mail` tests talk to `wiremock`/`axum` over plain HTTP, so
all 68 + 74 tests passing says nothing about HTTPS on Android. The panic above
is the concrete failure S3 must design around (an `HttpTls` runtime switch plus
either initialising rustls-platform-verifier through JNI or giving reqwest a
`webpki-roots`/bundled-root `ClientConfig`). The mTLS FDM path (`fdm_tls.rs`,
custom CA, aws-lc-rs provider) works on Android: `fdm_tls` 6/6 and
`fdm_https_mock` 3/3 pass with fixtures present.

Other engine-relevant observations for P1:

- `std::env::temp_dir()` falls back to `/data/local/tmp` on Android when
  `TMPDIR` is unset. The adb shell sets it, an app process does not, and an app
  cannot write there. Production code and tests that use `temp_dir()` must be
  given an app-private directory (`context.filesDir` / `cacheDir`) by the FFI
  layer. The `temp_dir()` uses found in `pos-db`
  (`migrate.rs`), `pos-core` (`config.rs`), `pos-mail` (`tem.rs`) and
  `pos-fiscal` (`counter.rs`) sit in `#[cfg(test)]` modules; the production
  code takes explicit paths, to be confirmed in P1.
- `chrono-tz` embeds its data, so no timezone database is needed.
- `rusqlite` bundled SQLite behaves the same (migrations, backups tests pass).

## tauri / src-tauri is not needed

```bash
cargo tree -p <crate> --target aarch64-linux-android -i tauri
# for pos-db, pos-fiscal, pos-print, pos-mail, pos-hubrise, pos-catalog:
error: package ID specification `tauri` did not match any packages
```

(six of six; `cargo tree -p pos-fiscal ... -i tauri 2>&1 | grep -q 'did not match'`
succeeds.) `Cargo.lock` is unchanged (no `cargo update` ran) and building any
of the six never touches `src-tauri`.

What the future engine (P1) still has to take from `src-tauri/src`, with no
code moved in this spike:

- `commands/*.rs`: 27 files, 9,909 lines, the cert commands. 20 files
  reference `tauri::` (`#[tauri::command]`, `tauri::State`); `access`,
  `bar_slip`, `errors`, `hubrise_push`, `mod`, `price_changes` and `signing`
  contain no `tauri::` reference and are already engine-shaped. The `do_*`
  inner functions that the SPF e2e tests call are the reusable core.
- `state.rs` (340 lines): `AppState` (db, poller db, config, shared reqwest
  client, poller wake-ups), no tauri types.
- `paths.rs` (102 lines) and `cli.rs` (242 lines): data/config directory
  resolution and CLI checks; Android replaces the path logic with app-private
  directories.
- `main.rs` (478 lines): setup, poller and outbox task wiring, window events;
  the Tauri-specific parts (`Builder`, window close, shell plugin) go away.
- Dependencies of `pili-pos` outside the six crates that the engine will need:
  `bcrypt`, `dirs` (replace on Android), `dotenvy` (probably drop),
  `tracing-subscriber`/`tracing-appender` (replace by logcat/file layer),
  `qrcode`, `pos-hubrise-types`, `pos-core`, `tokio-util`; `pos-peppol` is not
  in the cert build.
- `src-tauri/tests/*` (45 files, the SPF e2e harness) call the lib half of
  `pili-pos` and will have to move or be re-pointed at the engine crate.

Scope pointer: this belongs to P1 (P1b moves the UI rules into the engine).
