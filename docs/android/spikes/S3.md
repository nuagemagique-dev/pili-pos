# S3: TLS on Android (rustls-platform-verifier vs fixed roots)

Phase P0 spike for the Sunmi D3 Pro port. Branch `android/p0-S3`. Spike code is in
`spikes/s3/` (own Cargo workspace, own `Cargo.lock`) and is never merged to main; only this
report is. Plan reference: "The JNA gotcha" and "S3 TLS" in the approved plan.

## Verdict

1. The plan's assumption is **confirmed**: with the workspace feature set a default
   `reqwest::Client` builds fine on Android and **panics at the first HTTPS handshake**
   (`Expect rustls-platform-verifier to be initialized`, `rustls-platform-verifier-0.7.1/src/android.rs:90`).
2. **Both options work on the pili_api33 emulator** (Android 13, API 33, arm64): HTTPS GET to
   `https://api.hubrise.com` and `https://api.scaleway.com` succeeds with
   A (JNI init of the platform verifier, in a real release APK with R8, also with the .so loaded first by JNA),
   B1 (webpki-roots, preconfigured `ClientConfig`), B1c (webpki-root-certs, `tls_certs_only`),
   B2 (roots read at runtime from `/system/etc/security/cacerts`, preconfigured) and B2c (same, `tls_certs_only`).
3. **No reqwest 0.13 feature combination avoids compiling rustls-platform-verifier while keeping rustls.**
   Both public rustls features (`rustls`, `rustls-no-provider`) depend on it unconditionally.
4. **Recommendation: Option B, in the form B1c.** `HttpTls::RootsOnly(Vec<DER>)` handed to reqwest with
   `tls_certs_only`, roots compiled into the Android Rust workspace from `webpki-root-certs`
   (already in the root `Cargo.lock`), passed in by the host (pos-ffi), never read from the device.
   `HttpTls::Platform` stays what the Linux build does today, byte for byte. Details in "Recommendation".

Corrections to the task brief, found while doing the work:

- The Android component of rustls-platform-verifier is **not in the crate's tarball**. The crate
  `rustls-platform-verifier-android 0.2.0` is a 1-file version marker (`include = ["src/*"]`, `src/lib.rs` is doc only)
  and the `rustls-platform-verifier 0.7.1` tarball has no `maven/` directory either. The AAR is only published in the
  `maven-archive` branch of the GitHub repository (see "Option A", AAR distribution).
- The crate README's Gradle snippet declares the dependency as `rustls:rustls-platform-verifier`
  but its `resolutionStrategy` matches group `org.rustls`, and the published group is `org.rustls`
  (`.../maven/org/rustls/rustls-platform-verifier/0.2.0/`). Copy-pasting the README verbatim resolves a 404. The spike uses `org.rustls`.
- `cargo` on this Mac's default PATH is Homebrew's (`/opt/homebrew/bin/cargo`), which does not see the rustup
  `aarch64-linux-android` std and fails with `E0463 can't find crate for core`. The gates below need
  `PATH=$HOME/.cargo/bin:$PATH` (the rustup shim honours `rust-toolchain.toml`).

## Baseline: the problem, proven

`s3-probe baseline` builds `reqwest::Client::builder().timeout(20s).build()` and does the two GETs, each in a spawned
task so a panic is reported instead of killing `main`. Output on `pili_api33` (`adb shell`):

```
== baseline
mode=baseline reqwest-client-build:
  client built
PANIC: panicked at .../rustls-platform-verifier-0.7.1/src/android.rs:90:10:
Expect rustls-platform-verifier to be initialized
  GET https://api.hubrise.com -> TASK PANIC: task 5 panicked with message "Expect rustls-platform-verifier to be initialized"
PANIC: panicked at .../rustls-platform-verifier-0.7.1/src/android.rs:90:10:
Expect rustls-platform-verifier to be initialized
  GET https://api.scaleway.com -> TASK PANIC: task 7 panicked with message "Expect rustls-platform-verifier to be initialized"
exit=1
```

Without task isolation (`S3_NOSPAWN=1`, the panic reaches `main`): process exit code 101 right after `client built`.

Observed behaviour, precisely:

- **Building the client does not panic.** `Verifier::new` on Android only stores the crypto provider
  (`rustls-platform-verifier-0.7.1/src/verification/android.rs`, `Verifier::new`). reqwest calls it while
  building the client (`reqwest-0.13.5/src/async_impl/client.rs:759`). The panic is `global().expect(...)` at
  `src/android.rs:87-91`, reached only when a certificate chain is verified, i.e. at the **first HTTPS handshake**.
- Consequence for the engine: a plain-HTTP-only installation never trips it, and the failure is a latent panic on a
  tokio worker (the HubRise poller and mail outbox would lose their task, not report an error).

## Option B: fixed root set, platform verifier never touched

### APIs and the reqwest 0.13.5 source that proves the verifier is not constructed

Two APIs, both exercised:

1. **`ClientBuilder::tls_certs_only(certs: impl IntoIterator<Item = reqwest::Certificate>)`**
   (`reqwest-0.13.5/src/async_impl/client.rs:1902`; sets `config.tls_certs_only = true` at line 1904).
   In `ClientBuilder::build`, the `TlsBackend::Rustls` arm (line 689) only builds a `rustls_platform_verifier::Verifier`
   in the branch `else if !config.tls_certs_only` (line 750; `Verifier::new` at line 759, `new_with_extra_roots` at line 767).
   With `tls_certs_only` set that branch is skipped and the code takes the final `else` which calls
   `config_builder.with_root_certificates(crate::tls::rustls_store(config.root_certs)?)` (line 788; `rustls_store` is
   `src/tls.rs:639`, an empty `RootCertStore` plus the given certs). No platform verifier object exists on that path.
2. **`ClientBuilder::tls_backend_preconfigured(tls: impl Any)`** (`client.rs:2209`). A `rustls::ClientConfig` is downcast
   (`client.rs:2222-2226`) into `TlsBackend::BuiltRustls`, handled by the arm at `client.rs:644`, which hands the config to
   `ConnectorBuilder::new_rustls_tls` untouched. The `TlsBackend::Rustls` arm (the only one that names the platform verifier)
   is never entered. This is what `crates/pos-fiscal/src/fdm_tls.rs` already uses for the FDM.

Two pitfalls found in the source:

- `tls_certs_merge` (add roots on top of the platform ones) **cannot work on Android**: with extra roots and no
  `tls_certs_only`, `client.rs:763-781` returns the builder error `"rustls-platform-verifier could not load extra certs"` for
  `target_os = "android"`. Use `tls_certs_only` or a preconfigured config, never merge.
- `tls_backend_preconfigured` is type-matched by `Any` downcast to `rustls::ClientConfig` **of reqwest's own rustls**
  (`client.rs:2222`); a different rustls version in the engine silently becomes `UnknownPreconfigured`, which fails at build with
  `"Unknown TLS backend passed to use_preconfigured_tls"` (`client.rs:893-896`). That couples the engine to reqwest's
  rustls version, whereas `tls_certs_only` takes plain `reqwest::Certificate` (DER bytes) and has no such coupling.
  Another point for `tls_certs_only`.

### Variants implemented (`probe/src/main.rs`)

| Variant | Roots | reqwest API |
|---|---|---|
| B1 | `webpki_roots::TLS_SERVER_ROOTS` (121 trust anchors, compiled in) | `tls_backend_preconfigured(ClientConfig)`; the config is built like `fdm_tls.rs` (explicit aws-lc-rs provider, safe default protocol versions) with ALPN `h2`, `http/1.1` as reqwest sets itself |
| B1c | `webpki_root_certs::TLS_SERVER_ROOT_CERTS` (full DER certificates, compiled in) | `tls_certs_only(Certificate::from_der)` |
| B2 | every PEM block of every file in a directory given by path (`/system/etc/security/cacerts`, 125 files, 125 certificates, 0 unparsable), sorted by file name | `tls_backend_preconfigured(ClientConfig)` |
| B2c | same directory | `tls_certs_only(Certificate::from_der)` |

`webpki-roots` holds trust anchors (subject, SPKI), not full certificates, so B1 cannot feed `tls_certs_only`; that is why B1c uses
`webpki-root-certs` (full DER), which also happens to be in the root `Cargo.lock` already.

validity and host name; it is not a disabled verifier.

An empty root set is fail-closed: `tls_certs_only` with zero certificates leaves an empty `RootCertStore`, every handshake ends in `UnknownIssuer`.

## Option A: platform verifier with JNI init (built and run, not only desk-analysed)

### Wiring that works (`spikes/s3/android/`, `spikes/s3/jni-init/`)

- **Rust**: `cdylib` `libs3_jni.so` with `jni = "0.22.4"` (the version `rustls-platform-verifier 0.7.1` resolves to in the root lock; the API
  is the 0.22 one, `Env`/`EnvUnowned`, not 0.21's `JNIEnv`) exporting, through `#[jni_mangle("dev.pili.s3.Native")]`,
  `Java_dev_pili_s3_Native_init(Context)` which calls `rustls_platform_verifier::android::init_with_env(env, context)` exactly as the
  crate README prescribes, and `Java_dev_pili_s3_Native_get(String)`.
  `llvm-nm -D` shows `Java_dev_pili_s3_Native_init`, `Java_dev_pili_s3_Native_get`, `s3_get`, `s3_ping` and **no `JNI_OnLoad`**.
- **Kotlin**: `object Native { System.loadLibrary("s3_jni"); @JvmStatic external fun init(context: Context) }`, called once with
  `applicationContext` before any HTTPS request.
- **Gradle**: the `maven-archive` repository restricted to group `org.rustls`; `implementation("org.rustls:rustls-platform-verifier")` with the
  version forced from `Cargo.lock` (`rustls-platform-verifier-android` entry, 0.2.0) by the README's `ValueSource` + `resolutionStrategy`.
- **R8**: `-keep, includedescriptorclasses class org.rustls.platformverifier.** { *; }` (README "Proguard"). The AAR ships **no** consumer rules
  (`proguard.txt` absent from the AAR), so this rule is mandatory in the app. The release build (`isMinifyEnabled`, `isShrinkResources`) is what was tested.
- **Manifest merge**: the AAR's manifest contributes `android:networkSecurityConfig="@xml/network_security_config"` to `<application>`
  (verified in the built APK with `aapt2 dump xmltree`: `networkSecurityConfig(0x01010527)=@0x7f020000`). It lists about 27 KB of CRL hosts that may be
  fetched in cleartext. The POS app must not declare its own `networkSecurityConfig` without `tools:replace` and a merged copy of that list.
  (It does not affect raw-socket cleartext to the FDM over HTTP, which is outside the Java stack.)

The GETs run on a multi-thread tokio runtime inside the cdylib, so the handshake executes on a tokio worker that was never attached to the JVM; the
crate attaches per call (`with_context`, `attach_current_thread_for_scope`, `rustls-platform-verifier-0.7.1/src/android.rs:208-223`) and it works.

### Facts established

- **Init call site and lifetime.** `init_with_env` runs once per process: it fills a `OnceCell` (`android.rs:28`, `get_or_try_init` at `:98`), storing the `JavaVM`, a global
  reference to the `Context` and a global reference to its `ClassLoader` (`android.rs:97-117`). The first call wins; later calls are no-ops. Pass
  `applicationContext`, never an Activity (the global ref would leak it). The class loader comes from that context, which is why the Kotlin class
  `org.rustls.platformverifier.CertificateVerifier` is found from native threads. Init must happen before the engine can issue its first HTTPS call, so in
  the app it belongs in `Application.onCreate` (or the very first line of `EngineGateway.open`), on any thread.
- **Coexistence of System.loadLibrary init with JNA loading the same .so: proven** by scenario `A_jna`. JNA `dlopen`s `libs3_jni.so` without calling
  `JNI_OnLoad` (none exists anyway); `System.loadLibrary` afterwards resolves `Java_dev_pili_s3_Native_init` by symbol lookup. The Rust `static GLOBAL`
  filled by the JNI call is visible to calls made through JNA (the JNA `s3_get` failed before init and succeeded after), so both paths share one loaded image.
  This was with the default `extractNativeLibs=false` packaging (library mapped from the APK).
- **R8 and JNA** (finding for the UniFFI consumer rules): with only the usual JNA rules (`-keep class com.sun.jna.** { *; }`,
  `-keepclassmembers class * extends com.sun.jna.* { public *; }`) the JNA Library interface is optimised and `Native.load(...)` returns an object that is not the
  interface (`java.lang.ClassCastException` in the caller). Adding `-keep interface * extends com.sun.jna.Library { *; }` fixed it. UniFFI's generated
  `UniffiLib : Library` interface needs that rule in the `:pos-core` consumer rules.
- **R8 without the verifier keep rule** (`./gradlew assembleRelease -Ps3NoKeep`): init succeeds, then every handshake fails with
  `General("failed to call native verifier: Error")` and logcat shows
  `java.lang.ClassNotFoundException: Didn't find class "org.rustls.platformverifier.CertificateVerifier"`. Not a panic, but no HTTPS at all.
- **Failure mode if init is skipped**: panic at the first handshake on whatever tokio worker polls the connect future (`A_noinit` above, and the host
  baseline). Not at engine open, not at client build, so a test that only opens the engine would pass.
- **AAR distribution.** Only on GitHub (`https://github.com/rustls/rustls-platform-verifier/raw/maven-archive/android-release-support/maven/`, group
  `org.rustls`, artifact `rustls-platform-verifier`, versions 0.1.0, 0.1.1, 0.2.0). 10 295 bytes for 0.2.0 (sha1 `28b6b316c2749a7c94b4d19061f12c64759a0e27`),
  3 classes (`CertificateVerifier`, `StatusCode`, `VerificationResult`) plus the network-security-config. It is not on Maven Central and not in any crate.
  A reproducible Android build therefore depends on a GitHub raw URL at build time: acceptable only with Gradle dependency verification (sha256) or a vendored
  local Maven repo checked into the Android project.
- **What the platform verifier is**: it calls Android's `X509TrustManagerExtensions` with the system key store (the same directory B2 reads), so it honours the
  platform's trust decisions (OEM roots, network security config, revocation fetches the cleartext CRL list exists for).

Effort: Option A took about the half day the brief allows, including the three bugs above. It works, but it carries a JNI export, an AAR from GitHub,
a manifest merge, two R8 rules and an init ordering constraint.

## reqwest feature analysis: can rustls-platform-verifier be avoided?

reqwest 0.13.5 `Cargo.toml` feature table (read from the vendored source):

```
rustls             = ["__rustls-aws-lc-rs", "dep:rustls-platform-verifier", "__rustls"]
rustls-no-provider = ["dep:rustls-platform-verifier", "__rustls"]
__rustls           = ["dep:hyper-rustls", "dep:tokio-rustls", "dep:rustls", "__tls"]
default-tls        = ["rustls"]
native-tls / native-tls-vendored = [... "__native-tls" ...]   # OpenSSL
```

`cargo tree -i rustls-platform-verifier --target aarch64-linux-android -e features` in `spikes/s3` (workspace feature set, truncated to the reqwest path):

```
rustls-platform-verifier v0.7.1
└── rustls-platform-verifier feature "default"
    ├── reqwest v0.13.5
    │   ├── reqwest feature "__rustls"
    │   │   └── reqwest feature "rustls"
    │   │       ├── s3-jni-init v0.0.0 ...
    │   │       └── s3-probe v0.0.0 ...
    │   ├── reqwest feature "__rustls-aws-lc-rs" ...
    │   ├── reqwest feature "__tls" ...
    │   ├── reqwest feature "http2" ...
    │   └── reqwest feature "json" ...
    └── s3-jni-init v0.0.0 ...        (direct dependency, Option A only)
```

Alternatives, from `spikes/s3/feature-probe` (`cargo tree -i rustls-platform-verifier --target aarch64-linux-android -e features --features <variant>`):

| Variant (reqwest features besides `json`, `http2`) | platform verifier compiled? | usable? |
|---|---|---|
| `rustls` (workspace set) | yes | the baseline |
| `rustls-no-provider` | **yes** (same `dep:rustls-platform-verifier`, tree shows `__rustls` via `rustls-no-provider`) | no gain, and you must install a provider yourself (`client.rs:2499-2510` panics otherwise) |
| `__rustls` alone (private feature) | no (`package ID specification rustls-platform-verifier did not match any packages`) | **does not compile**: `error[E0433]: cannot find module or crate rustls_platform_verifier` at `reqwest-0.13.5/src/async_impl/client.rs:759`, because the `TlsBackend::Rustls` arm is cfg'd on `__rustls` but names the crate |
| `native-tls` | no | pulls `openssl-sys 0.9.117` for Android (needs an OpenSSL cross build and a different trust story), rejected |
| none | no | no `tls_backend_preconfigured`/`tls_certs_only` (both are `#[cfg(feature = "__tls")]`/`__rustls`), no HTTPS at all |

Conclusion: **the crate is always compiled when rustls is used; the only lever is not constructing or initialising it at runtime** (Option B), and that is safe
because on Android `Verifier::new` is a no-op that only keeps the crypto provider. Dropping it from the dependency graph would need a reqwest patch or fork, which
is not worth it. Effect on the crates:

- `pos-hubrise`, `pos-peppol`, `src-tauri`: `reqwest = { workspace = true }` (`rustls`, `http2`, `json`): unchanged; they receive an injected `reqwest::Client`.
- `pos-mail`: `default-features = false, features = ["json", "rustls", "http2"]`: unchanged; `TemClient::new` takes an injected client.
- `pos-fiscal`: `reqwest = { version = "0.13", features = ["json"] }` (defaults: `default-tls` = `rustls`, `charset`, `http2`, `system-proxy`) plus
  `rustls` with `aws_lc_rs`: unchanged, the verifier is compiled and **never used on the FDM mTLS path** (see inventory).
- Root `Cargo.lock`: untouched by this spike. Option B1c adds no crate to it (`webpki-root-certs 1.0.9` is already locked); B1 would add `webpki-roots`.

**Finding on the FDM path.** `FdmClient::tls_from_config` (`fdm_client.rs:493-505`) returns `None` when `fdm_url` is `https://` but `fdm_ca_file` is unset, or when
`fdm_tls::client_config` fails (the error is only logged; `config_problems` at `:472-489` reports it for display). The client is then a default
`Client::builder().build()`, so on Android an https FDM URL with a missing or unreadable CA file would reach the platform verifier and panic
inside a signing call instead of being refused cleanly as on Linux ("the FDM's certificate is then refused", doc comment at `:488-491`). That fallback client
must also come from the `HttpTls` factory (with `RootsOnly` it refuses cleanly with `UnknownIssuer`, which is the intended behaviour). Plain `http://` FDM URLs
(the SCE test machine and LAN FDMs) never handshake, so they are unaffected either way.

## Recommendation: Option B (B1c), behind `HttpTls`

### API sketch

Engine (`pos-engine`, no `cfg(target_os)` anywhere; the only reqwest TLS calls are `tls_certs_only` and `Certificate::from_der`):

```rust
/// Chosen by the host at Engine::open, never inferred from the OS.
pub enum HttpTls {
    /// Exactly today's behaviour: reqwest's default client (rustls-platform-verifier).
    /// Linux/Tauri passes this. No tls_* call is made.
    Platform,
    /// Trust exactly these roots (DER), nothing else. Empty list is refused at open.
    RootsOnly(Vec<Vec<u8>>),
}

impl HttpTls {
    /// The single place that touches reqwest TLS builder options.
    pub fn client_builder(&self) -> Result<reqwest::ClientBuilder, HttpTlsError> {
        let b = reqwest::Client::builder();
        match self {
            HttpTls::Platform => Ok(b),
            HttpTls::RootsOnly(ders) if ders.is_empty() => Err(HttpTlsError::NoRoots),
            HttpTls::RootsOnly(ders) => {
                let certs = ders.iter().map(|d| reqwest::Certificate::from_der(d)).collect::<Result<Vec<_>, _>>()?;
                Ok(b.tls_certs_only(certs))
            }
        }
    }
}
```

Call sites to replace `reqwest::Client::builder()` with `http_tls.client_builder()?`: `state.rs:98`, `delivery.rs:77`, and the `None` fallback of
`fdm_client.rs:427`. `fdm_tls.rs` and the preconfigured FDM config stay as they are.

Host (`pos-ffi`, in `android/rust/`, the only crate allowed to know about Android): UniFFI enum `HttpTlsMode { Platform, BundledRoots, RootsDir(String) }`.
`BundledRoots` expands to `RootsOnly(webpki_root_certs::TLS_SERVER_ROOT_CERTS.iter().map(|c| c.as_ref().to_vec()).collect())`; `RootsDir(path)` reads the
PEM files of a directory (B2, used for a support-supplied extra root or for diagnosing a device) with the loader in `probe/src/main.rs`. Kotlin passes
`BundledRoots` on Android. The Tauri `src-tauri` passes `Platform`. The Android build never calls `rustls_platform_verifier::android::init_*`, so there is
no JNI export for TLS, no AAR, no Gradle repository and no R8 rule for it.

### Against the criteria

- **Certification determinism.** Same engine source for both targets; the TLS behaviour is a pure function of `EngineConfig.http_tls` and the root bytes. With
  `BundledRoots` the root set is a build input pinned by `android/rust/Cargo.lock` (the `webpki-root-certs` version), so two builds of the same tag trust the same
  roots on every device and the APK reproducibility check (`check_repro`) covers it. Option A's verdict depends on JVM state (was `init` called, was the AAR
  kept by R8, which OS store and network security config the device has). B2 depends on the device's OS image (125 roots on this emulator; `webpki-roots` has 121).
- **No `cfg(target_os)` in the engine.** Satisfied: the engine sees an enum. Option A would need either an engine-side init hook or the host to guarantee ordering.
- **Root-store freshness and update path.** `BundledRoots`: bump `webpki-root-certs` in `android/rust/Cargo.lock`, ship a new APK through the app updater; the Mozilla set
  changes a few times a year and HubRise (Let's Encrypt via ISRG Root X1) and Scaleway (Sectigo via USERTrust RSA) chain to long-lived roots. The device store
  (A, B2) is updated by Sunmi OS releases; from my knowledge (not verified here) Android 13 has no Mainline update path for root certificates (that arrives with
  the Conscrypt APEX in Android 14), so a POS left on an old Sunmi image goes stale silently. A stale bundled set fails closed with a clear `UnknownIssuer`.
- **Operational failure modes.** B1c: unknown CA -> `UnknownIssuer` error (a normal `reqwest::Error`, logged and retried by the outbox); empty list refused at open.
  A: skipped init -> panic on a tokio worker that kills the HubRise poller or mail task silently; missing R8 rule -> all HTTPS fails with an opaque
  `failed to call native verifier`; manifest merge conflicts with an app-level `networkSecurityConfig`; AAR fetched from GitHub at build time.
- **Effect on the Linux v1.1 build.** With `HttpTls::Platform` the code path is `reqwest::Client::builder()` followed by exactly the existing options: no
  `tls_certs_only`, no preconfigured config, same `rustls-platform-verifier` use as today. No feature flag, dependency or lock entry changes in the root workspace
  (`webpki-root-certs` is needed only by `pos-ffi` in `android/rust/`). Any source edit still produces a new binary hash for the Linux certified build (that is a P1/freeze
  matter, not specific to TLS), but the HTTPS behaviour of the Linux build does not change.

### Known trade-offs of B (accepted)

- No revocation checking: the platform verifier on Android does fetch CRLs (that is what the cleartext CRL host list in the AAR is for); webpki without CRLs does not.
  Acceptable here (HubRise and TEM are not payment-critical and are authenticated by tokens), reqwest also offers `ClientBuilder::add_crl` with `tls_certs_only` if ever needed.
- A corporate TLS-inspecting proxy with a private root would not be trusted; `RootsOnly` with an extra root from the USB bundle (`RootsDir` or an extra DER) is the intended answer.
- Cold `Client` build with about 125 roots is negligible next to a handshake (not measured separately).

### Fallback

If the owner ever requires "trust what the device trusts", Option A is a working, tested recipe (this report), to be built in `pos-ffi` only and selected as a third
`HttpTlsMode::PlatformJni`. It should not be the default for the reasons above.
