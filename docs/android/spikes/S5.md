# S5: reproducible APK build (linux/amd64 container)

Status: done. Two clean builds of the S2 release APK in separate linux/amd64 containers give the
same SHA-1 for the signed APK and for every `lib/arm64-v8a/*.so`. Repeated in four independent
sessions (eight builds with remapping on): all pairs match.

Spike code (not merged to main, only this report is): branch `android/p0-S5`, `spikes/s5/`,
commits `2afb7db` and `7c5b020`.

## What was built

- **Source project:** the S2 spike (`spikes/s2`), copied read-only from the S2 worktree at S2
  commit `367e8f1794d444bdfec3083e685a1dce42a78d90` (`docs(android): add S2 UniFFI hello-world
  spike report`, branch `android/p0-S2`). The script takes the source path as its argument, makes
  a `git archive HEAD .` snapshot of it (clean tree, so no working-tree files are involved) and
  never writes there. The S2 worktree was `git status` clean before and after.
- **Project facts:** AGP 8.9.1, Kotlin 2.2.20, R8 8.13.25 forced, Gradle 8.11.1 (wrapper),
  compileSdk 36, minSdk 33, `isMinifyEnabled = true`, one cdylib (`hello-ffi`, UniFFI 0.32.2,
  tokio) plus the JNA AAR (`libjnidispatch.so`). Release APK: 23 zip entries, 1,202,706 bytes.
- **Files:**
  - `spikes/s5/Dockerfile`: the pinned image.
  - `spikes/s5/check_repro_apk.sh`: host driver (build image, make keystore, two builds, compare).
  - `spikes/s5/build_in_container.sh`: one clean build inside the container.
  - `spikes/s5/repro-init.gradle`: Gradle init script (determinism settings, test-key signing),
    so the S2 project is not modified.
  - `spikes/s5/apk_entry_diff.py`: per-entry APK comparison (diffoscope-lite).
  - `spikes/s5/probe_signing.sh`: re-signing determinism probe (RSA versus ECDSA).

## Signing

- A throwaway RSA-2048 keystore (`keytool -genkeypair -keyalg RSA -keysize 2048 -sigalg
  SHA256withRSA`) is generated once per check, inside the container, into a temp dir that is
  mounted read-only into both builds and deleted when the script exits (a `trap`). It is never
  committed or copied anywhere else. No keystore, APK or .so is in the repo.
- AGP signs through the init script: `enableV1Signing=false`, `enableV2Signing=true`,
  `enableV3Signing=true`.
- `apksigner verify --verbose --print-certs` (build-tools 35.0.0) output for the gate run:
  `Verifies`, v1 false, v2 false, v3 true, v3.1 false, 1 signer, `key algorithm: RSA`, `key size
  (bits): 2048`. Note that v2 shows false only because at the manifest minSdk of 33 apksigner
  verify considers v3 enough. The APK does carry both blocks: `apksigner verify --min-sdk-version
  24` gives v2 true and v3 true, and `--min-sdk-version 24 --max-sdk-version 27` gives v2 true
  (shown in the script output, `apksigner-verify.txt` and `probe_signing.sh`).
- **apksig determinism.** The v2/v3 signing block holds a signature over a digest of the zip
  contents. It has no timestamp and no random field. For an RSA key apksig uses RSASSA-PKCS1-v1_5
  with SHA-256, and PKCS#1 v1.5 signatures are deterministic: same key plus same input gives the
  same signature bytes. ECDSA signs with a fresh random nonce, so the same key and input give
  different signatures every time. Measured by `probe_signing.sh` (gate run): re-signing the same
  APK twice with the RSA key gives the same SHA-1 (`32b80f35...`, both times), and twice with a
  fresh secp256r1 key gives two different SHA-1 (`e832766a...` and `7d5b53c7...`). Same result in
  every session. So the signed APK is only byte-reproducible with an RSA key. Consequence for P3: the production key must be RSA if the SHA-1 of the
  signed APK is the value of record.
- The signed APK SHA-1 also depends on the certificate, so it differs between checks (each
  check makes a new key): 4 sessions gave 4 different APK SHA-1 with identical `.so` and
  identical entry contents (below). Within a check both builds use the same key.

### Negative control (remap off)

Session C ran the same two builds with `S5_NO_REMAP=1` and different build paths (`/build/src`
and `/build/other`):

- the unstripped `.so` leaked the paths (`/build/src` once, `/opt/cargo` 18 times) and its SHA-1
  differed between the runs (`a9d8fb76163fb3c5617b8d0ef5337f7c875e4e77` against
  `e06eaa166ae2431ae522a6f0cc83588eb87f2510`), so the remap is what makes it reproducible;
- the stripped `.so` inside the APK did not leak `/build/src` (AGP strips the debug info that
  held it) and matched between the runs (`350fb53c5ed5ec35f88295abfbc55c860f696955`), so the APK
  hash matched too (`360ab51037602965d6a63299f08d6234c384e33c`);
- the stripped `.so` still carried 16 `/opt/cargo` strings (panic locations of registry crates),
  and its size differs from the remapped build (627,128 against 626,952 bytes). With a different
  `CARGO_HOME` between two machines it would differ, which is the case the remap protects.

Conclusion: for this project, AGP's stripping hides most of the path leakage in the packaged
`.so`, but the unstripped file and any registry-path strings are not reproducible without the
remap. Keep the remap in P3.

## Problems met while building the image (fixed)

- First image build failed with exit code 141 at the sdkmanager step: `yes | sdkmanager
  --licenses` ends with SIGPIPE under `set -o pipefail`. Fixed with `sdkmanager --licenses <
  <(yes)`.
- Docker prints a lint warning for the build, `FromPlatformFlagConstDisallowed: FROM --platform
  flag should not use constant value "linux/amd64"`. It is kept on purpose so the Dockerfile
  cannot silently build for arm64; the build still succeeds.
- The first Dockerfile started with `# syntax=docker/dockerfile:1`, which pulls an unpinned
  frontend image. Removed (nothing in the file needs it).
- The sdkmanager NDK install (JVM unzip of a 650 MB archive under Rosetta) is the slowest image
  step but takes only 74 s on a quiet host. I briefly replaced it by a direct download and then
  reverted, so the final Dockerfile installs build-tools, platform and NDK all through sdkmanager.

## Limits and open points for P3

- **Maven artifacts are not checksum-pinned.** The Gradle distribution is verified, and the
  version of AGP, Kotlin, R8, JNA, coroutines and androidx is fixed in the project, but the
  artifacts are fetched from Google Maven and Maven Central without `gradle/verification-
  metadata.xml`. P3 should generate it (`gradle --write-verification-metadata sha256`) and commit
  it.
- **Network during the build.** Both runs download Gradle, Maven artifacts and crates. P3 should
  vendor or pre-fetch them (`cargo vendor`, a Gradle dependency cache layer) and run the build
  step with `--network none`, so a drifting upstream cannot change the result.
- **sdkmanager trust.** build-tools, platform and NDK are checked against sha1 values read from the
  same Google origin, over TLS. The sha1 values are recorded in this report and in the
  Dockerfile comments; the Dockerfile cannot fail on them by itself. Installing the three zips
  with explicit `sha1sum -c` is an option if that matters.
- **Cost.** The S2 crate set is tiny (uniffi, tokio). A build is 9 to 15 minutes under
  emulation including downloads. The real workspace will cost more in the cargo step; the NDK
  has no arm64 Linux host build, so the reference build stays linux/amd64 under Rosetta.
- **One architecture tested.** Both builds ran on the same M1 under Rosetta. A native x86_64
  Linux host (CI runner) was not tested; cross-compiled output should not depend on it, but the
  P3 exit check must be run once there.
- **Image digest of record.** The image is built from the Dockerfile, not pulled by digest. P3
  should push it to a registry and record its digest next to the APK SHA-1.

## How this generalises to P3 (`scripts/android/check_repro.sh`)

1. Same structure: build image once, then two builds in fresh containers from a `git archive` of
   the commit, no shared directories, fixed build path, `SOURCE_DATE_EPOCH` taken from the commit
   time instead of a constant, determinism settings in the build files rather than an init
   script.
2. **The real signing key stays outside the container.** The container builds the unsigned
   release APK (AGP without a signing config, zipaligned). The check then compares the two
   unsigned APKs byte for byte (no signature, so no key dependence), and prints the entry manifest
   as a second view. Signing with the real key happens afterwards on the host or in the release
   job, with the pinned build-tools `apksigner` (`--v1-signing-enabled false`, v2 and v3 on).
3. **What to compare against the installed APK.** The SHA-1 of record for an installed device is
   the SHA-1 of the signed APK. Anyone without the key can only check the unsigned digest or the
   entry manifest of the installed APK (strip the APK Signing Block, or compare zip entries as
   `apk_entry_diff.py` does) and verify the signature with `apksigner verify --print-certs`
   against the pinned certificate digest. Anyone with the key can re-sign and get the same bytes,
   but only because the key is RSA (see signing above).
4. Decisions to feed into DECISIONS.md: RSA production key (not EC), no key rotation lineage in
   v3, fixed minSdk (it changes whether the v2 block is emitted), image digest and Gradle
   verification metadata recorded with each release.
5. The frozen-Linux comparison in the plan (`check_repro` reproduces the frozen Linux SHA-1 at
   phase exits) is a different SHA-1 (Linux binary); this spike only covers the Android APK.
