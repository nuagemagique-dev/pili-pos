## 2. The relayed SD card question

The user asked: "I know we can put a SD card in the Sunmi D3 Pro, it will be on what the SQLite will be stored? How big should be the SD card do you think?"

**Where the SQLite lives: not on the SD card.** The engine database is `filesDir/engine/pos.db` in the app's private internal storage, with its post-Z backups (`filesDir/engine/backups/`), `engine.lock`, the nightly exports (`filesDir/engine/exports/`), the installed bundle (`filesDir/provisioning/`) and the logs (`filesDir/logs/`) (`provisioning/ProvisioningPaths.kt`, `EnginePaths::under` in `crates/pos-engine/src/engine.rs`). This is deliberate and enforced (PD220, gate check `plat-manifest`): the manifest has no `android:installLocation` and no storage permission, so Android can never move the data onto a card adopted as internal storage, and cloud backup and device transfer are off. A fiscal journal on removable media could be pulled out in the middle of a write, swapped, corrupted or read elsewhere; the SCE rules want the journal under the till's control.

**What the card is for.** Only as a removable medium, like a USB stick: the manager's SPF export (pos.db, the 7 newest backups, logs, audit, `MANIFEST.sha256`) and the update "from a stick". The card is never the only copy of anything.

**How big.** The P6 exit measured the growth on the emulator (P6-exit.md, PLATFORM.md section 12), and these measured figures replace the earlier 16 or 32 GB estimates of P5 and X1:
- 6,471 bytes per one-line sale, 14,336 bytes per six-line sale;
- so `pos.db` grows by about 236 to 523 MB a year at 100 sales a day, 0.7 to 1.6 GB a year at 300;
- one export set is about 8 database sizes (pos.db plus 7 backups): about 2 to 4 GB after a year at 100 sales a day.

Recommendation (unchanged from P6): a **microSDXC card of 64 GB**, "high endurance" or A1/U3, from a known brand, **formatted exFAT** (FAT32 refuses files of 4 GiB or more), enough for the first year at about 100 sales a day; **128 GB** at about 300 sales a day or from the second year. Larger brings nothing for this use. The largest card the D3 Pro accepts is hardware residue (no real D3 Pro here).

**What matters more than the card:** the engine keeps every post-Z backup on internal storage and never deletes one (PD219), which fills the till within months. A retention rule needs an engine change with the re-freeze; it is open question 2 of P6-exit.md.

**What P7 adds:** the 24 h soak (P7-T12) measures the growth again under a realistic mix (tables, refunds, split payments, a Z per compressed service day) and writes bytes per sale, bytes per Z and the projected card size into `docs/android/SOAK.md`. Until then the P6 figures above are the answer.

### 4.2 Scenario format (format 1)

```json
{
  "format": 1,
  "id": "M111",
  "ids": ["M111"],
  "title": "short English description",
  "fixture": "docs/20260821_UC_BasicSet_POS_FDM_1.8/M111_signSale_Refund",
  "fixtureDeviations": [{ "path": "transaction.transactionLines.0.mainProduct.productId", "reason": "same reason as the Linux test" }],
  "compare": { "status": "ignore" },
  "steps": [
    { "cmd": "login", "args": { "insz": "94060242576", "pin": "1111" } },
    { "cmd": "create_order", "args": { "input": { "order_type": "takeaway", "table_number": null, "user_insz": "94060242576" } }, "save": "order" },
    { "cmd": "checkout", "args": { "orderId": "$order.id", "payments": [{ "method": "cash" }] }, "save": "sale", "expect": { "fields": { "success": true } } },
    { "cmd": "fdm_control", "args": { "errors": ["FDM_LOCKED"] } },
    { "cmd": "checkout", "args": { "orderId": "$order2.id", "payments": [{ "method": "cash" }] }, "expect": { "error": "FDM_LOCKED" } },
    { "cmd": "fdm_control_reset", "args": {} }
  ]
}
```

- Required: `format` (1), `id`, `ids` (the UC ids this scenario covers; empty only for SMOKE), `title`, `steps`. Optional: `fixture` (a directory of the official UC folders, relative to the repository root), `fixtureDeviations`, `compare.status` (`ignore` default, `shape` for Q100 and Q110).
- `cmd`: one of the vocabulary of section 4.3. `args`: an object; for an engine command exactly the `invoke` argument object of `ui/src/api/ipc.ts`.
- **References:** any JSON string value of the form `$name.path` (whole string) is replaced by the value at `path` of the result saved under `name`; `path` is dot separated, numbers index arrays (`$order.lines.0.id`). A reference to a name not saved by an earlier step is an error.
- `save`: stores the result JSON under that name.
- `expect` (default `{}`): `{}` means the call returns no error and, when the result is an object with a `success` field, `success` is true; `{"fields": {...}}` additionally requires each listed field (dot paths allowed) to equal the value; `{"error": "CODE"}` requires an error whose code is `CODE` (the `code|k=v` prefix of the engine error string, `PosException.Coded` code on Android) or a result with `success` false whose `error` starts with `CODE`.
- `"repeat": N` on a step runs it N times (default 1).

### 4.4 Journal format (format 1, both sides)

```json
{
  "format": 1,
  "side": "android",
  "group": "10_basic",
  "scenario": "020_M111",
  "ids": ["M111"],
  "posSwVersion": "pili-pos-android/1.0.0-dev",
  "steps": [{ "cmd": "checkout", "ok": true, "error": null, "result": { "success": true, "fiscal_event_id": 3 } }],
  "fdm": [{ "operation": "signSale", "request": {}, "response": {} }],
  "statusCalls": [{ "request": {}, "response": {} }],
  "tickets": ["text of each printer job, in print order"],
  "verdict": "PASS"

```

`fdm` holds the non-Status calls of `GET /mock/requests` in order (the mock keeps the last 100 calls, so the host clears the log before each scenario); `request` and `response` exactly as the mock logged them. `statusCalls` holds the Status calls. `tickets` are the printer mock's job texts (`GET /jobs`, `GET /jobs/{id}`). `verdict` is PASS when every step met its `expect`.

### 4.5 Comparison checks (`pos-uc-check compare`)

Per scenario, one line `UCCHECK | <group>/<scenario> | PASS|FAIL | <checks>`, then `UCCHECK | total | PASS|FAIL | <n> failed (<m> scenarios)`, exit 1 on any FAIL:

| Check | Rule |
|-------|------|
| `steps` | both journals PASS, same commands, same `ok` per step |
| `fdm-ops` | same list of operations |
| `fdm-business` | `business_view` of every request equal, in order |
| `fdm-counters` | (operation, eventLabel, eventCounter, totalCounter) from each response's fdmRef equal (skipped with `--no-counters`, live mode) |
| `fdm-full` | the whole requests equal once the volatile paths of `UC.md` are removed |
| `sw-version` | Android `posSwVersion` starts with `pili-pos-android/`, the reference with `pili-pos/`; every request carries its side's value |
| `tickets` | same number of tickets, equal texts after normalisation (dates, times, signatures, QR payloads, software version line, device id; each rule in `UC.md`) |
| `fixture` | with `--fixtures` and a `fixture` field: the matching request's `business_view` equals the fixture's `GQL-Variables.json` one, except the listed `fixtureDeviations` (a listed deviation that does not occur is a FAIL) |
| `status-shape` | only when `compare.status` is `shape`: same keys in the Status responses |

`--report FILE` writes `{"format":1,"generated":"<ISO>","reference":"engine on the host","scenarios":[{"group","scenario","ids","checks":{"<check>":"PASS|FAIL|SKIP"},"verdict"}]}`.

## 9. Risks

- **Parallel P8 lane.** It also appends to `DECISIONS.md` and probably registers an owner in `LANES.md`: keep both at the merge. It may need the emulator for evidence captures; the soak of wave 6 holds `sunmi_d3_pro_api33` for up to 24 h and T11 holds the GMS AVD. The orchestrator schedules P8's emulator work outside those windows, or P8 waits (`p7_soak.sh status`).
- **Shared Mac.** 16 GB RAM, about 42 GB free disk at planning time. `android/uccheck` adds a host build of the engine (several GB under `target/uccheck`); heavy builds go through `heavy.sh`; workers delete their own large leftovers.
- **Interpreter drift.** Two interpreters of one vocabulary can disagree on an argument; T10 is where the full run proves they agree, and it may fix both.
- **Fixture deviations.** The Linux fixture tests list intended deviations in code (`Deviation`); scenario authors must mirror them with the same reasons, never invent new ones.
- **Emulator durability.** `adb emu kill` ends qemu without a guest shutdown; data the guest kernel had not written is lost, which is the case we want, but the host page cache still holds qemu's writes, so it is milder than a real plug pull. The real plug pull stays a D3 Pro runbook item.
- **Soak length.** If the 24 h run dies early for an environment reason (host sleep, another agent's `adb kill-server`), the 4 h acceptance stands and the exit report says so.
- **Unmeasured hardware** (unchanged): the real Sunmi serial, the Epson, the real SD card and USB stick, Play Protect on a real GMS device, deep sleep and thermal behaviour, a real plug pull.
