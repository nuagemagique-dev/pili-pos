### Emulator sharing

S1, S2 and S3 each need the emulator. To run them in parallel without stepping on each other, each card starts its own read-only instance on a fixed port and sets `ANDROID_SERIAL`:

| Card | Command | Serial |
|------|---------|--------|
| S1 | `emulator -avd pili_api33 -read-only -port 5554 -no-window -no-audio -no-snapshot -memory 2048 &` | `emulator-5554` |
| S2 | same with `-port 5556` | `emulator-5556` |
| S3 | same with `-port 5558` | `emulator-5558` |

Wait with `adb -s $ANDROID_SERIAL wait-for-device` and poll `getprop sys.boot_completed` until `1`. Kill your own instance at the end: `adb -s $ANDROID_SERIAL emu kill`. If memory pressure makes three instances impractical, serialise emulator use (S1, then S2, then S3) rather than sharing a serial.

### Docker sharing

P0.1 (`check_repro.sh`, `capture_fdm_journals.sh`) and S5 run heavy linux/amd64 builds under emulation. Never run two of them at the same time: check `docker ps` before starting one.

## Rules (reviewer checks on every card)

- Never push, never merge, never touch other worktrees or the main checkout. S5 may **read** `moyun-pos-wt/p0-S2`, never write it.
- Linux build inputs untouched: `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, `src-tauri/`, `ui/`, `crates/`, `deploy/`, `.github/`, and every existing file under `scripts/`.
- Spikes live in `spikes/sN/` with their own `[workspace]` and own `Cargo.lock`; nothing is added to the root workspace.
- No live calls to module2 or HubRise production services. Local mocks only, plus unauthenticated HTTPS GETs to public endpoints for TLS handshakes (S3).
- No secrets, keystores or build artifacts committed (`.so`, `.dylib`, `.apk`, `.aar`, `.dex`, `.jks`, `.keystore`, `.p12`, `.pem`, `.key`). `gradle-wrapper.jar` is the only allowed binary.
- Conventional Commits. No em-dash character anywhere (code, docs, commit messages).
- Spike cards make two kinds of commits: spike code (`spikes/sN/**`) and the report (`docs/android/spikes/SN.md`). The report commit touches only `docs/android/**`.
- Results are measured, never invented. A step that cannot finish in its time box is recorded as such, with the reason and the command to rerun it.

**Acceptance:**
- Script is executable, `bash -n` clean, shellcheck clean if available, works from any cwd.
- Two consecutive inventory runs give a byte-identical file.
- `--diff` exits 0 on the committed baseline and exits 1 (listing the line) against a copy with one line deleted.
- Section totals match the binaries' own counts.
- BASELINE.md has no invented hash or journal; any hash is cross-checked against the copied build_info files.
- Nothing from `scripts/e2e_hubrise/hubrise.secret` or any token lands in `docs/android/baseline/`.

## Card S3: TLS spike (lane A)

- **Depends on:** none. **Needs human:** no.
- **Allowed globs:** `docs/android/spikes/S3.md`, `spikes/s3/**`

**Background:** with the `rustls` feature, reqwest 0.13 uses rustls-platform-verifier 0.7.x (0.7.1 in the root `Cargo.lock`).
- On Android it panics at the first HTTPS handshake unless `init_with_env` ran with a JNIEnv and a Context.
- It also needs the `rustls-platform-verifier-android` Kotlin component, shipped in the crate's `maven/` dir.
- UniFFI loads the library through JNA, which never calls `JNI_OnLoad`.
- The FDM mTLS path (`crates/pos-fiscal/src/fdm_tls.rs`, `tls_backend_preconfigured`) is unaffected.

**Work:**
1. `spikes/s3/` has its own workspace, using the same reqwest and rustls versions and features as the root lock.
2. Baseline: a default `reqwest::Client` binary on `emulator-5558` shows the failure (or the report explains why it does not).
3. Option B:
   - B1: webpki-roots compiled in;
   - B2: roots read at runtime from `/system/etc/security/cacerts`, passed in by path;
   - both feed a rustls `ClientConfig` passed through `tls_backend_preconfigured`, or the root-only reqwest 0.13 API;
   - cite the reqwest source (file:line) showing the platform verifier is never built on that path;
   - HTTPS GET to `https://api.hubrise.com` and `https://api.scaleway.com` from a cargo-ndk binary on the emulator.
4. Option A:
   - a cdylib with a `Java_..._init` JNI export, using the `jni` version rustls-platform-verifier 0.7.1 depends on, which calls `init_with_env`;
   - Kotlin calls it through `System.loadLibrary` + `external fun`;
   - Gradle wiring of the crate's maven repo, plus keep rules;
   - the same two GETs from an app or instrumented test on the emulator.

   If this exceeds about half a day, write a thorough desk analysis instead and say so explicitly. It must cover the init site and lifetime, coexistence with JNA loading the same .so, R8 rules, AAR distribution, and the failure mode when init is skipped.
5. Feature analysis: can any reqwest 0.13 feature set avoid compiling rustls-platform-verifier? Evidence: the reqwest Cargo.toml feature table and `cargo tree -i rustls-platform-verifier -e features`. Assess the impact on pos-hubrise, pos-mail and pos-fiscal.
6. Inventory every client construction with file:line, using `grep -rn 'Client::builder\|ClientBuilder' crates src-tauri`. That includes `src-tauri/src/state.rs` (shared_http), `src-tauri/src/commands/delivery.rs` (MailState::from_config) and `crates/pos-fiscal/src/fdm_client.rs`.

**Acceptance:**
- Status lines shown for both hosts under B1 and B2, with no panic. No credentials or bodies sent.
- Option A is either proven on the emulator or covered by an explicitly labelled desk analysis.
- The feature question is answered with evidence.
- The recommendation picks one option for `HttpTls::{Platform, RootsOnly(..)}` and includes an API sketch. It argues the choice against:
  - certification determinism;
  - no `cfg(target_os)` in the engine;
  - root-store freshness and its update path;
  - failure modes;
  - zero behaviour change for the Linux build.

**Gates:**

## Card S5: Reproducible APK spike (lane B)

- **Depends on:** S2, soft. Build the Dockerfile and image right away; run the two-build check once S2 has a commit whose `assembleRelease` passes. Fall back to `spikes/s5/minimal/` only if S2 is unavailable.
- **Needs human:** no.
- **Allowed globs:** `docs/android/spikes/S5.md`, `spikes/s5/**`

**Work:**
1. `spikes/s5/Dockerfile`, linux/amd64:
   - base image pinned by digest;
   - JDK 17 pinned;
   - cmdline-tools zip verified by sha256;
   - sdkmanager with exact platform, build-tools and NDK 27.1.12297006;
   - Rust 1.99.0 via sha256-verified rustup-init, plus `aarch64-linux-android`;
   - `cargo install --locked cargo-ndk --version 4.1.2`.
2. `spikes/s5/check_repro_apk.sh <source dir>`:
   - builds the image;
   - runs twice from a clean snapshot of the source, with no shared project build dirs;
   - collects the signed APK and `lib/arm64-v8a/*.so`;
   - compares SHA-1 values;
   - on mismatch, prints per-entry sha256 diffs of the unzipped APKs.

   The source defaults to a read-only copy of `moyun-pos-wt/p0-S2/spikes/s2`, recording its commit, and never writes there.
3. Determinism:
   - `SOURCE_DATE_EPOCH`;
   - `--remap-path-prefix` for cargo home, rustup home and the source dir;
   - `CARGO_INCREMENTAL=0`;
   - recorded codegen-units and LTO;
   - Gradle `isPreserveFileTimestamps = false` and `isReproducibleFileOrder = true`;
   - `vcsInfo` off;
   - `TZ=UTC`, `LANG=C.UTF-8`;
   - a fixed build path.
4. Signing:
   - a throwaway **RSA** keystore generated once per check inside the container and reused for both builds;
   - v1 off, v2 and v3 on;
   - checked with `apksigner verify --verbose --print-certs`.

   RSA PKCS#1 v1.5 signatures are deterministic for the same key and input; ECDSA is not, so it would break the comparison. A new key per run would break it too.

**Acceptance:**
- Every version and checksum appears in the Dockerfile and the report.
- The report records:
  - image build time, per-run build time under emulation, image size;
  - both SHA-1 values (APK and each .so) and whether they match;
  - on mismatch, the differing zip entries and the identified cause, plus the fix applied or proposed;
  - if the build does not finish in about 3 hours, where it stopped and why;
  - how this carries over to P3: `scripts/android/check_repro.sh`, the real key held outside the container, comparing the APK without its signature block.
- Docker leftovers cleaned up and disk use recorded. No keystore, APK or .so committed.

## After review

1. The reviewer writes `docs/android/phases/P0-review.md`. For each card it records the gate reruns (long Docker gates may rely on the recorded logs when time-boxed, which the review states), the findings at file:line, and a verdict of APPROVE, REWORK (at most 2 rounds) or ESCALATE.
2. Approved items land on `android/p0` following the merge procedure above.
3. The planner drafts `docs/android/DECISIONS.md` (P0.7) from the reports and writes `P0-exit.md` with the gate evidence, hashes, risks and open questions. S4 and the deviceId decision stay open until the device is available.
4. **Exit:** the user approves DECISIONS.md. Then `android/p0` may be merged into main, after fetching and comparing with origin using the gh credential helper. Never force-push.
