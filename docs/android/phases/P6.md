## The relayed question: SD card in the Sunmi D3 Pro

The user asked: "I know we can put a SD card in the Sunmi D3 Pro, it will be on what the sqlite will be stored? How big should be the SD card do you think?"

**Where the SQLite lives.** Not on the SD card. The engine database is `filesDir/engine/pos.db` (app-private internal storage), next to `filesDir/engine/backups/`, `filesDir/provisioning/` and `filesDir/logs/` (`provisioning/ProvisioningPaths.kt`). It stays there by design (PD220):
- a fiscal journal on removable media can be pulled out, swapped, corrupted or read by another device;
- the app has no `android:installLocation`, so Android never moves its data to an SD card adopted as internal storage; P6-T2 adds a gate check that keeps it so;
- backup to the cloud and device transfer are off (`allowBackup=false`, the exclude-everything `data_extraction_rules.xml`).

**What the SD card is for.** It is a removable volume like a USB stick, so it is a target of the SPF export (P6-T6), of the update source "from a stick" (P6-T7) and later of the nightly export lane. Spike S4 proved the SAF export on exactly that kind of volume (a virtual SD card stood in for the USB stick). `DISALLOW_MOUNT_PHYSICAL_MEDIA` stays off so it mounts.

**Size, first estimate.** A test database of this repository holds about 1.6 KB per fiscal event and 3.5 KB per pending sign (19 events, measured with `dbstat`). With the order, its lines and payments, that is roughly 10 to 15 KB per sale, so 100 to 300 sales a day give roughly 0.4 to 1.5 GB a year. The P4 exit report said "megabytes per year"; that was too low. P6-T11 measures the real growth per sale on the emulator and writes it into `docs/android/PLATFORM.md`.

**A finding that matters more than the card size.** The engine writes a full copy of `pos.db` to `backups/` after every Z (`crates/pos-engine/src/commands/signing.rs:761`) and never deletes one. After a year that is about 365 copies of a database that keeps growing, which is far more than the database itself and can fill the till's internal storage within months. P6 deletes nothing (the engine is frozen and deleting is a decision for the user, PD219); the About screen shows the free internal space and the size of `backups/`, and the export copies only the newest backups. A retention rule (for example "keep 14 days locally") is an engine change for the user, best done with the re-freeze that the nightly export already needs.

**Recommendation.** A good-quality microSDXC card of 64 GB, "high endurance" or A1/U3 class, formatted exFAT:
- exFAT because FAT32 refuses files of 4 GiB or more, and a database plus its copies can reach that over the years;
- 64 GB holds many full exports even after several years.

The largest card the D3 Pro accepts and its slot behaviour were not checked: that is hardware residue (no real D3 Pro here). The SD card is never the only copy: the SPF export is a manager action, and the off-till copy belongs to the nightly export lane.

- **PD210 SPF export** (AM Art. 16/102; Linux practice: `FEUILLE_ACQUISITION_DONNEES_FR.md` section 7 = full `pos.db`, logs, SHA-1 of the binary). The flow follows Q17:
  - a manager-only screen, refused while an order or takeaway is open;
  - pre-check of a mounted removable non-primary volume ("Insert the USB stick or SD card");
  - picker `StorageVolume.createOpenDocumentTreeIntent()` from the locked activity (never `FLAG_ACTIVITY_NEW_TASK`), the root refused with the hint to create `PILI-EXPORT`;
  - a persisted grant per volume uuid, and "Change folder" releases the old grant.

  Export folder `pili-export-<yyyyMMdd-HHmmss>-<deviceId>` with:
  - `pos.db` (a fresh `backupDatabase()`);
  - `backups/` (the 7 newest older backups);
  - `backups.txt` (inventory of every backup: name, bytes, SHA-256);
  - `logs/` (engine logs);
  - `audit/` (platform audit files);
  - `identity.json`;
  - `LISEZMOI.txt` (French, brand-neutral: what the files are, how to check `MANIFEST.sha256` with `shasum -a 256 -c`);
  - `MANIFEST.sha256` (sha256sum format), written last.

  There is no staging copy: each file is hashed while it streams to the volume, `fd.sync()`, then read back through the content resolver and hashed again. A mismatch fails the export. Nothing on the volume is deleted, even on error. A write failure on a file of 4 GiB or more says "the stick is probably FAT32, use exFAT". Every export is audited (files, bytes, result).

  - the current user is Admin (`getCurrentUser`);

  Question for the user: an engine `update_precheck` (booking period closed, no pending sign) together with the re-freeze.

- **PD215 Install flow** (Q18). Order:
  1. preconditions;
  2. verification (PD211, PD212: minisign, JSON, package, versionCode strictly greater than the installed one, download, SHA-256 and SHA-1, archive info: package, versionCode, versionName, signer set equal to the installed one and to `signerSha256`);
  3. `backupDatabase()`;
  4. `EngineGateway.close()`;
  5. a fsynced marker `filesDir/platform/update/pending.json`;
  6. the audit row "started";
  7. a PackageInstaller session (`MODE_FULL_INSTALL`, `USER_ACTION_NOT_REQUIRED`, `INSTALL_REASON_POLICY`), committed with an explicit mutable PendingIntent to `InstallResultReceiver`.

  Afterwards:
  - **Refusal:** no session, the file is deleted.
  - **Failure status:** audit, marker deleted, engine reopened with `EngineService.start`.
  - **`STATUS_PENDING_USER_ACTION`:** the session is abandoned and recorded as an error.
  - **Success:** the "done" row is written by the new process (`UpdateCompletionHook`, from the marker).
  - **Restart:** `PackageReplacedReceiver` starts `MainActivity`.
  - **No rollback:** a faulty version is fixed by a newer declared version (DECISIONS 6).
