## 1. Goal

The plan update of 2026-10-08 puts a **nightly export** into v1.0, for Linux and Android, built once in the engine:

1. right after every real Z (manual or automatic), an **encrypted full backup** of `pos.db`: a consistent SQLite online backup, encrypted with age to the per-installation recipients of `pos.json` (owner key, optional producer key); the receiving server can never read it;
2. a **cleaned statistics copy**: a separate SQLite with its own stable, versioned schema holding sales only (tickets, lines with product code and quantity, channel table/takeaway/delivery/online, totals per VAT rate, payments, discounts, refunds, Z totals, terminal), users as pseudonymous ids, and no NISS, no PIN hash, no token, no customer e-mail;
3. an **export outbox** with retries that uploads both files plus a SHA-256 manifest by HTTPS PUT to a generic per-installation endpoint (URL and bearer token file in a new optional `export` section of `pos.json`, off when absent), keeps the last N days locally and never blocks a sale or the Z;
4. the **status** (last export, last error, pending) through new engine commands, shown in the Linux Vue Settings and in a dedicated Android Compose screen;
5. **tests** (engine unit and integration tests, a mock receiver, the privacy proof of the statistics copy, a decrypt round trip with a test key) and the **dossier** text in French, brand-neutral.

Out of scope: the real receiver and the statistics dashboard (later, outside the certified scope), the re-freeze `linux-v1.0.0-rc1` and the rename of the version to 1.0.0 (the user's), any pos.db schema change, any SD card use.

## 2. The relayed question: SD card in the Sunmi D3 Pro

The user asked whether the SQLite database would be stored on an SD card in the D3 Pro and how big the card should be.

- **No.** The engine opens `files/engine/pos.db` in the app's private internal storage (set up in P4), and X1 puts the local exports next to it, in `files/engine/exports/`. A fiscal journal on removable media could be pulled out, swapped, corrupted or read by another app; internal app storage is also excluded from Android backup (`allowBackup=false`). On Linux everything stays under `/var/lib/pili-pos`.
- **Removable media** stay reserved for the manager's SAF export of P6 (SPF access: backups, logs, manifest), where the stick or card is only a transfer medium.
- **Space.** The database of one till holds text rows; it should grow by megabytes per month, not gigabytes (not measured yet). With the default `keep_days` of 14, the local exports hold 14 encrypted copies of the database plus 14 small statistics files, so a database of 50 MB would take under 1 GB of internal storage. X1-T6 measures the three files of its test day and the exit report gives a better estimate.
- **If an SD card is used for the P6 export**, a good-quality 16 or 32 GB card (Class 10 / A1) is ample. The largest card the D3 Pro accepts was not checked.

### 3.2 Configuration (X1D5)

```json
"export": {
  "url": "https://receiver.example/installations/abc",
  "token_file": "export_token",
  "owner_recipient": "age1...",
  "producer_recipient": "age1...",
  "keep_days": 14
}
```

- Absent: no export at all, nothing created.
- `url`: https; plain http only to `127.0.0.1`, `localhost`, `[::1]` or `10.0.2.2` (tests, emulator).
- `token_file`: the bearer token, trimmed, never in `pos.json`; resolved relative to a provisioning bundle like the other files.
- `owner_recipient` required, `producer_recipient` optional: age X25519 public keys. The private keys never reach the till or the server.
- `keep_days`: default 14, 1 to 365.
- A malformed section is reported by `PosConfig::problems()` and `install::check_config_source` (so `pili-pos --check-config` and the Android bundle check refuse it); `Engine::open` never fails because of it, the export is disabled and the status shows the problem.

### 3.3 Trigger, isolation, catch-up (X1D6)

- The Z path (`signing::follow_up`, ReportZ, not training) only wakes the export worker. Manual and automatic Z share that path; a Z found at start-up is caught by the cursor.
- The worker runs in its own background loop (first pass at start, then every `export_outbox` tick, 60 s by default, or on a wake), outside the signing lock, on a separate read-only SQLite connection and `spawn_blocking` threads. The Z answer, its printouts and the next sale never wait for it.
- Each pass: prepare every real Z newer than `exports/cursor.json` within `keep_days`; upload what is due; apply the retention. First enable: the cursor starts just before the latest Z (that Z only, no history backfill).

### 3.4 Files and layout (X1D7)

```
<data_dir>/exports/
  cursor.json             {lastZReportNo}
  status.json             {lastError, lastErrorAt, lastUploadedId, lastUploadedAt, dropped}
  pseudonym.key           32 random bytes, mode 0600, never exported
  .tmp/                   work area, emptied at start-up and before each preparation
  20261008-z000042/
    pos-20261008-z000042.db.age      age-encrypted SQLite online backup of pos.db
    stats-20261008-z000042.sqlite    cleaned statistics copy, schema v1
    manifest-20261008-z000042.json   format pili-export/1, ids, hashes
    state.json                       {exportId, createdAt, zReportNo, bookingDate, uploaded, attempts, nextAttemptAt, lastError}
```

The plaintext snapshot exists only in `.tmp/<id>/` and is deleted right after encryption; an export directory appears only complete (rename from `.tmp`).

### 3.5 Upload protocol (X1D8)

- `PUT <url>/<export_id>/<file name>`, headers `Authorization: Bearer <token>`, `Content-Type`, `X-Content-SHA256`, `User-Agent: pili-export/1`.
- Order: backup, stats, manifest (the manifest last marks a complete export).
- 2xx success; anything else retried after 1, 2, 4 ... minutes, capped at 60, without limit; 401 and 403 show as `unauthorized (HTTP 401)`.
- Client from the engine's `HttpTls`, 120 s per file; file read into memory, above 512 MiB refused.
- Retention: export directories older than `keep_days` are deleted, sent or not; an unsent one counts in `dropped`.

### 3.6 Statistics copy v1 (X1D9)

Tables: `meta`, `users(user_ref, role)`, `tickets`, `ticket_lines`, `ticket_vat`, `ticket_payments`, `ticket_discounts`, `z_report`, `z_vat`, `z_payments`. Only the sales (N events) and the Z of the booking period closed by that Z; no training, presence, copy, order, pro forma, drawer, money or invoice event. Channel from the order type and source (dine-in table, till takeaway, online delivery or online). Refunds as kind `refund` with negative amounts. Amounts as signed by the FDM. `user_ref` = `u-` + 16 hex characters of SHA-256 over a domain tag, the per-installation key and the INSZ; the system identity is `system`. Receiver-facing description: `crates/pos-export/STATS_SCHEMA.md`.

Directory exports/<export_id>/ holds pos-<id>.db.age (SQLite online backup of pos.db, binary age format, recipients owner and optional producer), stats-<id>.sqlite (cleaned copy of the booking period closed by that Z, schema v1), manifest-<id>.json (format pili-export/1: export id, pos_id, terminal_id, pos_sw_version, Z number, booking date, creation time, stats schema version, the recipients' public keys, and name, size and SHA-256 of the two data files) and state.json. An export is built in exports/.tmp/ and renamed into place when complete; the plaintext snapshot exists only there and is deleted after encryption; .tmp is emptied at start-up and before each preparation.
- **X1D8 Upload.** HTTPS PUT of <url>/<export_id>/<file name> with Authorization: Bearer <token>, Content-Type and X-Content-SHA256, in the order backup, stats, manifest (the manifest last marks a complete export). 2xx is success; any other answer or a transport error is retried after 1, 2, 4 ... minutes, capped at 60, without limit; 401 and 403 show as unauthorized. The client comes from the engine's HttpTls with a 120 s timeout per file; a file is read into memory (the reqwest stream feature is not added to the cert build) and a file above 512 MiB is refused with an error. Local exports older than keep_days are deleted whether sent or not; an unsent one deleted that way is counted in dropped and logged.
- **X1D9 Statistics copy v1.** Tables meta, users (user_ref, role), tickets, ticket_lines (product code, name, department, quantity, prices, VAT label and rate, discount), ticket_vat, ticket_payments, ticket_discounts, z_report, z_vat, z_payments. Channel table, takeaway, delivery or online from the order type and source; refunds are tickets of kind refund with negative amounts; only the sales (N events) and the Z of that period: no training, presence (S), copy, order (P), pro forma, drawer, money or invoice event. Users are pseudonyms: user_ref is u- and 16 hex characters of SHA-256 over a domain tag, a 32-byte per-installation key (exports/pseudonym.key, created once, mode 0600, never exported, not inside pos.db so not in the backup either) and the INSZ; the system identity is system. No INSZ or NISS, user name, PIN hash, token, e-mail, phone, address, customer name, HubRise payload, ticket text or signature. The receiver-facing description is crates/pos-export/STATS_SCHEMA.md.
- **X1D10 Commands.** Two new cert commands, export_status and export_run_now (Access::Admin, async), each a one-call Tauri wrapper, an engine function (do_export_status, do_export_run_now) and an FFI method of PosEngine: the cert command count goes from 84 to 86. ExportStatus (camelCase JSON, i64 counts, RFC 3339 UTC times): enabled, problem, endpoint (scheme, host and port only), keepDays, lastExportId, lastPreparedAt, lastUploadedId, lastUploadedAt, pending, nextAttemptAt, lastError, lastErrorAt, kept, dropped. export_run_now makes every pending export due now, wakes the worker and returns the status at once. No new error code (errors.rs unchanged, so the Android error tables and their tests do not move) and no new event topic (the screens poll the status every 30 s while shown).
- **X1D11 Linux UI.** A panel of SettingsView (ui/src/components/ExportStatusPanel.vue), admin only. Its texts are in ui/src/i18n-export.ts with a local lookup, deliberately not merged into ui/src/i18n.ts, so scripts/android/vue_to_android.mjs and the generated Android strings stay unchanged.
- **X1D12 Android screen.** Package dev.nuagemagique.pilipos.nightly: route nightly, a FeatureEntry and a SettingsEntry (id nightly.export, managerOnly, order 800), strings_nightly.xml in fr, en and zh with the prefix nightly_, engine calls only through EngineGateway. A new LANES.md owner nightly and the prefix in lane_paths.py are the lane's only foundation edits, appended lines only, made by X1-T9 as a shared card; its wave partner X1-T10 touches only the dossier, so no file is shared within the wave.
- **X1D13 Dossier.** French and brand-neutral: a new EXPORT_NOCTURNE_FR.md, and updates of the data sheet section B (networks and devices: the connection to the installation's own receiver), REPONSES_MANUEL_CERT_FR (Internet configuration, DAS recap, cloud question), SECURITE_BD_FR (backup security), FEUILLE_ACQUISITION_DONNEES_FR and PROFIL_ENTREPRISE_FR (GDPR minimisation), the installation and user manuals, MANIFEST.txt and the PDFs. The legal framing (the legal record stays local; the export is a copy and not a cloud POS) is the planner's draft for the user's review.
- **X1D14 Storage on the device (the user's SD card question).** pos.db and the exports stay in internal storage: on Android in the app's private files directory (files/engine, exports in files/engine/exports), on Linux under /var/lib/pili-pos; X1 writes nothing to an SD card. Removable media stay reserved for the manager's SAF export of P6. X1-T6 measures the three files for its test day; the exit report gives an estimate of the space needed.

## 9. Risks

- **Freeze checks on android/int** fail for every lane after the merge until the re-freeze (X1D3). Mitigation: merge order and x1_gate.sh on android/int.
- **age dependency weight.** age brings its own crates (x25519, chacha20poly1305, i18n-embed and others) into the cert graph and the Android `.so`; size and build time grow. X1-T2 reports the added package count; `x1-lock-additive` proves no existing version moved.
- **Memory on Android.** A file is read into memory for the upload (X1D8); a database of a few hundred MB on a 4 GB device is the limit; the 512 MiB refusal protects the process.
- **Disk.** About 30 GB free shared by three lanes; each card builds the root workspace and android/rust. Cards stop under 6 GB free.
- **check_ui_parity (UI lane).** If the UI lane's `check_ui_parity.py` requires a Kotlin call site for every `ipc.ts` command, `export_status` and `export_run_now` are covered by the `nightly` package; verify after the merge.
- **LANES.md merge.** X1-T9 appends to LANES.md; if another lane appends at the same spot the integrator resolves a trivial conflict.
- **Restore changes pseudonyms.** The pseudonym key lives outside pos.db; a database restored on a new machine gets new pseudonyms (documented, accepted).
- **Hardware residue.** HTTPS from the real D3 Pro to a real receiver is not tested (no receiver yet); the FFI test covers the Android code path on the host and the engine path is identical.
