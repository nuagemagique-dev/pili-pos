# Android port: P0.1 baselines

What the Linux/desktop product looks like before the Android port starts.
Phases P1 and later are checked against these files: the test inventory
(`scripts/android/test_inventory.sh --diff`), the reproducible Linux
binary SHA-1, and the FDM request journals of the HubRise end-to-end flow.

## 1. Test inventory

File: `docs/android/baseline/test_inventory.txt`
(sha256 `586834f05390ed4535e34b22747d2a34c0f003542676684e0de8d8b0ff7f99a2`).
Generated by `scripts/android/test_inventory.sh`, built from the real test
binaries (`cargo test --no-run --message-format=json`, then each executable
with `--list --format terse`, plus `cargo test --doc -- --list` per library).
Line format: `<section>:<package>::<target-kind>:<target-name>::<test path>`.
Two consecutive runs produced a byte-identical file (`cmp` clean).

| Section | Command | Tests listed | Sum of the `N tests` the binaries report |
|---------|---------|-------------:|-----------------------------------------:|
| `ws` | `cargo test --workspace` (default features: hubrise + peppol) | 1355 | 1355 |
| `cert` | `cargo test -p pili-pos --no-default-features --features cert` | 491 | 491 |
| both sections | lines in the file | 1846 | 1846 |
| distinct tests | section prefix dropped | 1355 | |

- `cargo test --workspace` was also run for real (exit 0): 1342 passed, 0 failed,
  13 ignored, i.e. 1355 = the `ws` figure. The 13 ignored tests are listed by
  `--list`, so they count in the inventory.
- No doctest exists in the workspace (every `cargo test --doc` listing reports
  `0 tests`); the doctest path of the script is in place for when one appears.
- The `cert` section is a strict subset of `ws`: the only pili-pos tests in `ws`
  and not in `cert` are the 2 `spf_e2e_basic::m150_*` invoice tests (493 in
  `ws`, 491 in `cert`; the cert build has no invoicing). It adds no test name
  of its own.

**Which total is the plan's "~1,356"?** The comparable figure is the `ws`
section (equivalently the distinct total), which is **1355**, one less than
the plan's 1,356. I found no source for the plan's 1,356 (a grep of the repo's docs,
README, CLAUDE.md and scripts finds no such figure); the difference
of 1 is unexplained and is most likely a count taken at another commit or
from a run summary. The `cert` total (491) and the 1846 line total are not
comparable to it, since the cert tests are re-runs of ws tests under another
feature set. **Consequence for later gates:** "tests never drop" must be
checked against this baseline (`test_inventory.sh --diff`, which fails when a
committed line disappears), not against a hard-coded 1,356, which the current
tree already misses by one.

Gate check: `scripts/android/test_inventory.sh --diff` reports
`baseline 1846 lines, current 1846 lines: 0 added, 0 removed` and exits 0.
Deleting a line from a copy of the baseline and passing it with `--baseline`
reports 1 added; adding a bogus line reports it as removed and exits 1.

## 3. FDM request journals (`scripts/e2e_hubrise.sh` flow)

Captured by `scripts/android/capture_fdm_journals.sh`, which runs the same
flow (real cert binary vs `pos-hubrise-mock`, `pos-fdm-mock`,
`pos-printer-mock`, WebDriver in a Linux arm64 container) without editing
`scripts/e2e_hubrise.sh` or `scripts/e2e_hubrise/*`: it builds from a temp
copy of that directory whose `inside.sh` EXIT trap also does
`curl -s http://127.0.0.1:8081/mock/requests > /logs/fdm_requests.json`.
It uses its own container and docker volumes, so a concurrent
`scripts/e2e_hubrise.sh` is not disturbed. The suite passed both times
(8 tests, 0 failures), the journal holds 9 calls each time (the mock keeps
the last 100, so nothing was truncated), in this order:

`Status, signWorkIn, signSale, Status, signSale, Status, signOrder, signSale, Status`

Nothing leaves the machine; no HubRise or module2 service was contacted.

| File | sha256 |
|------|--------|
| `fdm_journal_hubrise_e2e_run1.json` (raw) | `b48c018a92d1efb8bf541a5daaf7bbbf1b148cdff1e92055a257e0dff82f7a0e` |
| `fdm_journal_hubrise_e2e_run2.json` (raw) | `0946d5c3f60c3cf19c14dec59720f56df9ec24ca724c2f0317fe2a753dcd17c7` |
| `fdm_journal_hubrise_e2e_run1.normalised.json` | `68a09ee31caa69a39864de47bb71313f949034b7da86d93fbd3af3b01c073473` |
| `fdm_journal_hubrise_e2e_run2.normalised.json` | `68a09ee31caa69a39864de47bb71313f949034b7da86d93fbd3af3b01c073473` |

The two raw journals differ (timestamps, counters, signatures, uuids) but the
two normalised ones are byte-identical, which is what a later phase compares
against (`jq -S` filter in `capture_fdm_journals.sh`, variable `NORMALISE`).

Fields dropped or replaced by normalisation:

- any object key `at` (when the mock logged the call);
- every key ending in `DateTime` (`posDateTime`, `fdmDateTime`, ...);
- `eventCounter`, `totalCounter` (the FDM's running counters);
- `digitalSignature`, `shortSignature`, `verificationUrl` (derived from the
  timestamps and counters);
- values replaced: uuid-shaped strings become `"<uuid>"` (`bookingPeriodId`),
  ISO date-time strings become `"<datetime>"`, bare `YYYY-MM-DD` strings
  become `"<date>"` (`bookingDate`, which follows the day of the run);
- keys are sorted (`jq -S`), so object order does not matter.

Kept as contract: operations and their order, query text, every request
variable (ticket numbers, ids, VAT breakdown, lines), and the responses'
amounts, labels and VAT calculations. The seed's employee INSZ and the mock
FDM identifiers appear in the journals; they are test data of the mock flow.
No token, secret or `hubrise.secret` content is in these files (the mock
FDM runs without a bearer token; `grep -i "secret|token|bearer"` finds
nothing in the raw journals).

To recapture: `scripts/android/capture_fdm_journals.sh --name <name> --out-dir <dir>`
(needs Docker, jq, node/npm; a first run builds the cert binary inside the
container, later runs reuse the `pili-e2e-p0-*` volumes).
